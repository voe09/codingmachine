# #infra

Archive coverage: 2025-04-30–2026-08-25 (UTC); 7,369 messages, including 2,445 thread replies. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1364827114670657616).

Review progress: every exported message body from April through July 2025 has been read chronologically (1,315 messages). The later-period sections below are selective and do not imply a complete reading of the remaining 6,054 archived messages.

## Early platform lessons: April–June 2025

The public-release discussion started from a reproducibility-versus-cost tension. Marin was described as a giant Makefile whose main experiment data could in principle be recreated, but serving tokenized data to outsiders was not just a storage decision: shuffled reads generated Class B object operations for each example, reportedly twice per example in that setup. A shuffle-buffer or preshuffled dataset was proposed to reduce access cost while lowering the barrier for speedrun contributors. By mid-May, a small speedrun had run fully locally using an HF-hosted dataset, though earlier local-GPU instructions had assumed `gs://` access and a gated download path failed for external users. The archive supports the design rationale and the small successful test, not a measured 64-fold cost reduction. [Recreation model](https://marin-discord.pages.dev/#1364827114670657616/1367199175028117514) · [Storage-operation mechanism](https://marin-discord.pages.dev/#1367200372283801711/1367201423229583400) · [Shuffle proposal](https://marin-discord.pages.dev/#1367200372283801711/1367201930132197480) · [Local-GPU barrier](https://marin-discord.pages.dev/#1364827114670657616/1369830146025984010) · [Local run](https://marin-discord.pages.dev/#1364827114670657616/1373185371751583834).

Shared clusters revealed that Ray's CPU and memory resource requests were *logical scheduling quantities*, not hard limits on what a task could consume. A data-overlap job wrote large inputs to `/tmp`, contributing to full worker disks and repeated us-central2 failures; another episode logged 64 workers killed for memory pressure. Raising the requested CPU/RAM per task reduced possible concurrency but was not itself memory enforcement. The group moved some disruptive work to a separate cluster and considered changing the head-node resource model. A Ray setting of `min_workers: 0, max_workers: 0` on the head template did **not** prevent CPU tasks from landing there; the prototype was `CPU: 0` plus a dedicated tiny `head_node` resource for the non-preemptible status actor. July's failures made that prototype's broader suitability uncertain. This is why resource declarations, placement, and isolation should be tested independently. [Scratch-space cause](https://marin-discord.pages.dev/#1364827114670657616/1370844865130266787) · [Worker OOMs](https://marin-discord.pages.dev/#1364827114670657616/1370904887558275173) · [Logical resources](https://marin-discord.pages.dev/#1364827114670657616/1379553892479533207) · [Head scheduling misconception](https://marin-discord.pages.dev/#1364827114670657616/1387914996142440449) · [Dedicated-resource prototype](https://marin-discord.pages.dev/#1364827114670657616/1387958835267768341) · [Later doubts](https://marin-discord.pages.dev/#1364827114670657616/1391885957766058124).

Dependency setup was a separate source of apparent job failure. Dolma's tokenizer-version conflict with Levanter/Transformers made its installation slow: `pip_dependency_groups` used a 600-second setup timeout, while `--pip_deps dolma` used 1,800 seconds and let the reported job proceed. Ray's runtime package could also expire before workers fetched it, and a generated MyPy cache enlarged one contributor's package enough to trigger upload trouble. A `draccus` import failed only on remote workers. Local success therefore did not establish that the actual shipped runtime environment had the same code and dependencies. [Dolma timeout diagnosis](https://marin-discord.pages.dev/#1367314548801015952/1367339935199400007) · [Package expiration](https://marin-discord.pages.dev/#1364827114670657616/1377466355502022697) · [Large-cache case](https://marin-discord.pages.dev/#1364827114670657616/1377713786919850036) · [Remote import failure](https://marin-discord.pages.dev/#1364827114670657616/1373879146593386536).

The early evaluation problems show why job liveness and evaluation breadth had to be separated. Hugging Face rate limits were bypassed in one SFT run by downloading data in an explicit prior step. An LM-eval-harness failure to load a task surfaced as `{'num_fewshot': 10}` even though the underlying problem appeared to be an HF download error. Running annealing without those in-loop tasks, or narrowing it to a stable signal and evaluating specialty benchmarks later, was proposed to keep training alive. The same local-disk concern appeared when concurrent evaluations filled `/tmp` with downloaded data; redirecting the relevant HF cache to `/dev/shm` was suggested. These were incident-specific workarounds, not a claim that MMLU alone is a sufficient evaluation suite. [Separate download](https://marin-discord.pages.dev/#1364827114670657616/1370526029411647519) · [Misleading task error](https://marin-discord.pages.dev/#1364827114670657616/1371356962637484142) · [Annealing proposal](https://marin-discord.pages.dev/#1364827114670657616/1372317550075187312) · [Eval scratch space](https://marin-discord.pages.dev/#1367200372283801711/1372676743231574138).

Version and ownership boundaries mattered operationally. A new Ray version was reported to interact badly with libtpu and prompted a revert; rebuilding a cluster image required more than running `make cluster_docker`—the team also needed to record the image ID, update cluster configs, and reboot the affected clusters. One operator found that a reserved v4-2048 had the same naming pattern as smaller v4-256 resources and might have been deleted during a recovery sequence, though the cause was not established. Separately, a vLLM TPU device-busy error was initially compared with a known lock-release race, but a cluster restart did not clear this instance, so the earlier diagnosis could not simply be reused. [Ray/libtpu interaction](https://marin-discord.pages.dev/#1364827114670657616/1382594093032411208) · [Image rollout steps](https://marin-discord.pages.dev/#1364827114670657616/1389326093525192765) · [Reserved-resource uncertainty](https://marin-discord.pages.dev/#1364827114670657616/1387145636847292538) · [Lock-race caveat](https://marin-discord.pages.dev/#1364827114670657616/1388057922415755336).

## July 2025: preemption and ownership

July's recurring placement-group failures were not simply lack of accelerator quota. A group name could remain allocated after a job controller was preempted, preventing a replacement from creating the same group. In a different Ray failure mode, repeatedly preempted nodes still appeared to the cluster as available, so jobs hung despite the dashboard showing resources. Participants debated removing placement groups, reclaiming them by name, and forward-porting an earlier preemption patch. One Ray state could report creation failure without returning a handle to remove the group, leaving it retrying indefinitely. These are distinct failures of resource *ownership* and resource *observation*. [Orphaned-group hypothesis](https://marin-discord.pages.dev/#1364827114670657616/1392353824684900373) · [Stale-node explanation](https://marin-discord.pages.dev/#1364827114670657616/1392175683798831247) · [Failed-commit state](https://marin-discord.pages.dev/#1364827114670657616/1397293973474902127).

The head-node fix also needed revision. Setting head CPU to zero plus a custom status-actor resource helped on central1, where tokenization had previously landed on the head and caused OOMs. A stale deployment config separately produced an infeasible head-affinity error; later, the team questioned whether zero CPU was appropriate on central2 and discussed node-affinity scheduling instead. A head-pinned `run_on_pod_ray` experiment improved some preemption recovery but did not fully solve SliceActor creation timeouts. No single configuration was shown to settle all these cases. [Central1 improvement](https://marin-discord.pages.dev/#1391885957766058124/1391888700325236766) · [Stale config](https://marin-discord.pages.dev/#1364827114670657616/1389434790821888070) · [Central2 doubt](https://marin-discord.pages.dev/#1364827114670657616/1391885957766058124) · [Controller experiment](https://marin-discord.pages.dev/#1364827114670657616/1396310453981810759) · [Residual timeout](https://marin-discord.pages.dev/#1364827114670657616/1396331645975400529).

Capacity, setup, and package-state failures frequently looked alike to an experimenter staring at pending jobs. Preemptible *quota* did not guarantee available TPUs; a later GCP operation explicitly reported no v4 capacity in us-central2-b. For large slices, Ray's cap on simultaneous SSH setup connections combined with big Docker pulls made a slice take roughly 40 minutes when a simpler script finished in about five, suggesting setup concurrency rather than allocation alone. At another point, an expired container image, unavailable v4 capacity, and a half-completed `uv` migration all overlapped. The July `uv` rollout also exposed that a `uv` virtual environment need not include `pip`, while Ray's nested task setup still invoked `python -m pip`. Pinning a dependency in the local environment was no substitute for checking `pip freeze` *inside* Ray workers. [Capacity error](https://marin-discord.pages.dev/#1364827114670657616/1394552627320328283) · [SSH setup cap](https://marin-discord.pages.dev/#1364827114670657616/1396393628351463525) · [Compound outage](https://marin-discord.pages.dev/#1364827114670657616/1394360272059236576) · [Ray/uv boundary](https://marin-discord.pages.dev/#1364827114670657616/1392281220355723375) · [Remote version check](https://marin-discord.pages.dev/#1390865747999461548/1390866487505322035).

Device cleanup revealed why deleting a lock file is not equivalent to freeing a TPU. After a remote task raised, a Ray worker process could remain alive holding `/dev/accel*`; a retry then failed to initialize the device. Removing the team's separate lock file did not release the device handle. The developers traced the earlier process ID and considered explicit child-process lifetime management or discarding an unhealthy slice, with multi-user safety called out for any cleanup actor. A targeted hack reportedly fixed one reproduction, but the channel still debated the right abstraction. [File versus device](https://marin-discord.pages.dev/#1364827114670657616/1399861854456778816) · [Process-ID evidence](https://marin-discord.pages.dev/#1364827114670657616/1399951413605564418) · [Cleanup alternatives](https://marin-discord.pages.dev/#1364827114670657616/1400275171633401940) · [Targeted workaround](https://marin-discord.pages.dev/#1364827114670657616/1400531543851536525).

## Reliability and scheduling

Most posts are transient job reports, but the recurring problem is reproducible training on preemptible, distributed accelerators. In 2025, Ray worker pressure, lost manual workers, and head-node failures repeatedly interrupted jobs. One run encountered 64 workers killed for memory pressure; another experiment tried pinning `run_on_pod_ray` to the head node so preemption recovery would be less fragile. The team's August reliability list called for explicit crash alerts independent of W&B, better worker reattachment, preempted-node cleanup, and retention of container images needed to restart clusters. [Worker pressure](https://marin-discord.pages.dev/#1364827114670657616/1370904887558275173); [preemption experiment](https://marin-discord.pages.dev/#1364827114670657616/1396310453981810759); [reliability agenda](https://marin-discord.pages.dev/#1364827114670657616/1409642552960880780).

That reliability problem had several independent layers. One July 2025 outage combined an expired container image, v4 TPU provisioning trouble, and a broken build during an incomplete `uv` migration. A training or evaluation failure could therefore be an artifact-availability, cluster-capacity, or dependency problem rather than one defect with one fix. GPU/TPU dependency resolution had its own failure mode: an upper bound in one package led the solver to an older version without that bound, then to a chain of incompatible old dependencies. The reported remedy was to refine pins incrementally. [Compound outage](https://marin-discord.pages.dev/#1364827114670657616/1394360272059236576); [dependency-solver mechanism](https://marin-discord.pages.dev/#1364827114670657616/1435754744596529163).

The Ray clusters moved to token authentication in January 2026 after security concerns about remote-code-execution exposure. The migration required a reboot, interruption planning, and fresh client authentication; running experiments needed checkpoints and resubmission plans. By February, Iris offered a region-aware `iris job run` path that could schedule across zones and removed some manually chosen storage-prefix settings. Iris itself still had a restart and state-recovery learning curve: a March controller restart lost state and required database recovery. These messages document a transition, not a claim that the new orchestrator had no failures. [Ray migration](https://marin-discord.pages.dev/#1364827114670657616/1456402718481711337); [Iris beta](https://marin-discord.pages.dev/#1364827114670657616/1476412061339619469); [controller recovery](https://marin-discord.pages.dev/#1364827114670657616/1486408175266824432).

Iris made job and log links shareable through a hosted dashboard, reducing dependence on local port forwarding. That improved collaborative diagnosis, but the group still had to separate controller, package setup, job, and training failures. A July vLLM-worker startup problem, for example, was a 300-second lock timeout while multiple workers fetched a Git dependency; it was not evidence that the model or inference kernel was broken. [Dashboard](https://marin-discord.pages.dev/#1364827114670657616/1493692493374554293); [dependency lock](https://marin-discord.pages.dev/#1364827114670657616/1525035072414023750).

Iris reservations tried to remove the burden of locating a free TPU slice: a job could request a device type, wait for allocation, and place child jobs in the allocated region. The March 2026 announcement warned that multiple reservations were not yet constrained to one region and that the data prefix should follow the selected region. A later autoscaler discussion proposed that equal-priority scale groups were chosen by configuration order rather than available capacity; the cited message is a diagnosis and proposed fix, not confirmation that this was the sole cause or that it had shipped. [Reservation behavior and caveat](https://marin-discord.pages.dev/#1364827114670657616/1478098597344973013); [autoscaler diagnosis](https://marin-discord.pages.dev/#1481718488748785664/1481775706458292295).

## Evaluation, artifacts, and cost

An evaluation job could appear to fail for reasons unrelated to the model. In October 2025, downloaded checkpoints accumulated in `/dev/shm/levanter-lm-eval` while cleanup deleted a different path, filling local storage. A February 2026 Evalchemy integration moved evaluation in-process, fixed bugs, and reported roughly 10x speedup; orphaned subprocesses had been keeping TPU devices locked after their parent died. Another investigation found that memray's failure to compress a profiler file was not the cause of task failures: the actual failures included benchmark-loading errors. The general diagnostic practice is to trace a symptom to the failing process, data path, and task outcome before changing training code. [Checkpoint-cache mismatch](https://marin-discord.pages.dev/#1422607680253464616/1423022712850350231); [Evalchemy update](https://marin-discord.pages.dev/#1364827114670657616/1471664293479972886); [profiler false lead](https://marin-discord.pages.dev/#1364827114670657616/1491210597172252762).

The team also considered narrowing *in-training* evaluation to a robust signal such as MMLU after CORE task downloads repeatedly killed annealing jobs, then running specialized benchmarks after training. That was a proposal to separate training liveness from breadth of evaluation, not an assertion that MMLU alone is sufficient. TPU CI had a related coverage trade-off: it ran only for explicit labels or selected paths, so changes outside the path list could break TPU behavior without a test firing. [Annealing-eval proposal](https://marin-discord.pages.dev/#1364827114670657616/1372317550075187312); [TPU CI trigger policy](https://marin-discord.pages.dev/#1364827114670657616/1367262649653661757).

Serving needed correctness checks under realistic load, not only startup and throughput checks. A June 2026 report said a vLLM TPU configuration using PyTorch/XLA with data parallelism above one generated corrupted or repetitive output increasingly under load. The reported lesson was to inspect traces and output quality before trusting an apparently live service; the Discord post did not establish a general failure of all vLLM-on-TPU configurations. [Load-dependent decode report](https://marin-discord.pages.dev/#1364827114670657616/1511756705468514325).

Checkpoint storage was estimated at roughly $60,000 per month. The ensuing retention debate exposed a real research trade-off: deleting checkpoints after one month would cut cost but could remove baselines needed for three- to six-month comparisons. A warning, ownership, and recovery policy was still under discussion in the cited exchange. The same resource-awareness appears in plans to use Parquet consistently and to cache tokenizers and dependency artifacts instead of repeating costly setup work. [Storage estimate](https://marin-discord.pages.dev/#1364827114670657616/1490767485547319388); [retention concern](https://marin-discord.pages.dev/#1364827114670657616/1490771304188481657); [tokenizer cache proposal](https://marin-discord.pages.dev/#1464369718457798819/1464445011503611957).

Placement and artifact size were operational costs too. A February 2026 warning said cross-region data reads were incurring more than $1,000 per day, so keeping compute near its input data mattered even when another region had available TPUs. Some workers lacked the 32 GB of free local disk needed to fetch what appeared to be an 8 GB model, illustrating that compressed model size was not a safe disk-capacity estimate. [Cross-region cost](https://marin-discord.pages.dev/#1364827114670657616/1472266105937592340); [worker disk example](https://marin-discord.pages.dev/#1364827114670657616/1461417585987027045).

## Reproducibility and access

Code and package state were recurrent experimental variables. A developer found that `ray_run.py` had read environment variables from another worktree, silently overriding a launch configuration. A later vLLM-TPU fork proposal required CI-built wheels, a versioned dependency, and a separately maintained fork rather than an untracked local build. These details affect whether someone else can rerun the same experiment. [Worktree configuration failure](https://marin-discord.pages.dev/#1364827114670657616/1403127593732931706); [fork packaging requirements](https://marin-discord.pages.dev/#1364827114670657616/1484638373128699986).

Version changes could alter the scientific budget itself: one user reported that moving from JAX 0.6.2 to 0.8.0 raised compile-time memory enough to halve the batch size that fit, from 128 to 64. For long-running hero jobs, a two-week Iris branch-age limit created a different tension: restarting after hardware failure could require pulling many unrelated main-branch changes mid-run. The discussion asked whether a pinned exception or selective updates would be safer; it did not settle a universal policy. [JAX memory regression](https://marin-discord.pages.dev/#1364827114670657616/1458293817043062876); [hero-run branch-age concern](https://marin-discord.pages.dev/#1364827114670657616/1521669792623366255).

Data caches can preserve a mistake as efficiently as a correct preprocessing step. An April 2026 audit said a beginning-of-sequence tokenizer bug had affected several tokenized corpora, including SWE-ZERO and protein documents, and prompted requests to delete or re-tokenize affected caches. The affected-set list was partly inferred by an agent and was still being checked with owners in the cited post; it should not be treated as a final inventory. [Tokenizer-cache audit](https://marin-discord.pages.dev/#1364827114670657616/1497036970851963113).

The group debated whether the experiment executor was formalizing scientific protocols or imposing maintenance overhead without delivering that benefit. A formal, runnable protocol could preserve decisions that a final-run report omits, especially for agent-led research. In practice, participants questioned whether executor code captured the protocol at all; one proposed retaining reproducible data preparation and named output artifacts while simplifying the model-training pipeline. This was an architectural debate, not a completed removal. [Protocol rationale and concern](https://marin-discord.pages.dev/#1364827114670657616/1519443077926748311); [data-cache versus model-pipeline distinction](https://marin-discord.pages.dev/#1364827114670657616/1519686532057927751).

Opening the platform to more contributors raised an access-control question: Iris did not yet strongly sandbox a limited-trust user from running arbitrary expensive code. Separately, attempts to use Marin models outside the monorepo showed how much implicit documentation and model setup agents depended on. These remained design and documentation needs, not solved operational properties. [Sandbox question](https://marin-discord.pages.dev/#1364827114670657616/1511845749430816879); [out-of-repo friction](https://marin-discord.pages.dev/#1364827114670657616/1518613966849445948).
