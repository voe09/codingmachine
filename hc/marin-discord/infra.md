## Early platform lessons: April–June 2025

The public-release discussion started from a reproducibility-versus-cost tension. Marin was described as a giant Makefile whose main experiment data could in principle be recreated, but serving tokenized data to outsiders was not just a storage decision: shuffled reads generated Class B object operations for each example, reportedly twice per example in that setup. A shuffle-buffer or preshuffled dataset was proposed to reduce access cost while lowering the barrier for speedrun contributors. By mid-May, a small speedrun had run fully locally using an HF-hosted dataset, though earlier local-GPU instructions had assumed `gs://` access and a gated download path failed for external users. The archive supports the design rationale and the small successful test, not a measured 64-fold cost reduction. [Recreation model](https://marin-discord.pages.dev/#1364827114670657616/1367199175028117514) · [Storage-operation mechanism](https://marin-discord.pages.dev/#1367200372283801711/1367201423229583400) · [Shuffle proposal](https://marin-discord.pages.dev/#1367200372283801711/1367201930132197480) · [Local-GPU barrier](https://marin-discord.pages.dev/#1364827114670657616/1369830146025984010) · [Local run](https://marin-discord.pages.dev/#1364827114670657616/1373185371751583834).

Shared clusters revealed that Ray's CPU and memory resource requests were *logical scheduling quantities*, not hard limits on what a task could consume. A data-overlap job wrote large inputs to `/tmp`, contributing to full worker disks and repeated us-central2 failures; another episode logged 64 workers killed for memory pressure. Raising the requested CPU/RAM per task reduced possible concurrency but was not itself memory enforcement. The group moved some disruptive work to a separate cluster and considered changing the head-node resource model. A Ray setting of `min_workers: 0, max_workers: 0` on the head template did **not** prevent CPU tasks from landing there; the prototype was `CPU: 0` plus a dedicated tiny `head_node` resource for the non-preemptible status actor. July's failures made that prototype's broader suitability uncertain. This is why resource declarations, placement, and isolation should be tested independently. [Scratch-space cause](https://marin-discord.pages.dev/#1364827114670657616/1370844865130266787) · [Worker OOMs](https://marin-discord.pages.dev/#1364827114670657616/1370904887558275173) · [Logical resources](https://marin-discord.pages.dev/#1364827114670657616/1379553892479533207) · [Head scheduling misconception](https://marin-discord.pages.dev/#1364827114670657616/1387914996142440449) · [Dedicated-resource prototype](https://marin-discord.pages.dev/#1364827114670657616/1387958835267768341) · [Later doubts](https://marin-discord.pages.dev/#1364827114670657616/1391885957766058124).

Dependency setup was a separate source of apparent job failure. Dolma's tokenizer-version conflict with Levanter/Transformers made its installation slow: `pip_dependency_groups` used a 600-second setup timeout, while `--pip_deps dolma` used 1,800 seconds and let the reported job proceed. Ray's runtime package could also expire before workers fetched it, and a generated MyPy cache enlarged one contributor's package enough to trigger upload trouble. A `draccus` import failed only on remote workers. Local success therefore did not establish that the actual shipped runtime environment had the same code and dependencies. [Dolma timeout diagnosis](https://marin-discord.pages.dev/#1367314548801015952/1367339935199400007) · [Package expiration](https://marin-discord.pages.dev/#1364827114670657616/1377466355502022697) · [Large-cache case](https://marin-discord.pages.dev/#1364827114670657616/1377713786919850036) · [Remote import failure](https://marin-discord.pages.dev/#1364827114670657616/1373879146593386536).

The early evaluation problems show why job liveness and evaluation breadth had to be separated. Hugging Face rate limits were bypassed in one SFT run by downloading data in an explicit prior step. An LM-eval-harness failure to load a task surfaced as `{'num_fewshot': 10}` even though the underlying problem appeared to be an HF download error. Running annealing without those in-loop tasks, or narrowing it to a stable signal and evaluating specialty benchmarks later, was proposed to keep training alive. The same local-disk concern appeared when concurrent evaluations filled `/tmp` with downloaded data; redirecting the relevant HF cache to `/dev/shm` was suggested. These were incident-specific workarounds, not a claim that MMLU alone is a sufficient evaluation suite. [Separate download](https://marin-discord.pages.dev/#1364827114670657616/1370526029411647519) · [Misleading task error](https://marin-discord.pages.dev/#1364827114670657616/1371356962637484142) · [Annealing proposal](https://marin-discord.pages.dev/#1364827114670657616/1372317550075187312) · [Eval scratch space](https://marin-discord.pages.dev/#1367200372283801711/1372676743231574138).

Version and ownership boundaries mattered operationally. A new Ray version was reported to interact badly with libtpu and prompted a revert; rebuilding a cluster image required more than running `make cluster_docker`—the team also needed to record the image ID, update cluster configs, and reboot the affected clusters. One operator found that a reserved v4-2048 had the same naming pattern as smaller v4-256 resources and might have been deleted during a recovery sequence, though the cause was not established. Separately, a vLLM TPU device-busy error was initially compared with a known lock-release race, but a cluster restart did not clear this instance, so the earlier diagnosis could not simply be reused. [Ray/libtpu interaction](https://marin-discord.pages.dev/#1364827114670657616/1382594093032411208) · [Image rollout steps](https://marin-discord.pages.dev/#1364827114670657616/1389326093525192765) · [Reserved-resource uncertainty](https://marin-discord.pages.dev/#1364827114670657616/1387145636847292538) · [Lock-race caveat](https://marin-discord.pages.dev/#1364827114670657616/1388057922415755336).

## July 2025: preemption and ownership

July's recurring placement-group failures were not simply lack of accelerator quota. A group name could remain allocated after a job controller was preempted, preventing a replacement from creating the same group. In a different Ray failure mode, repeatedly preempted nodes still appeared to the cluster as available, so jobs hung despite the dashboard showing resources. Participants debated removing placement groups, reclaiming them by name, and forward-porting an earlier preemption patch. One Ray state could report creation failure without returning a handle to remove the group, leaving it retrying indefinitely. These are distinct failures of resource *ownership* and resource *observation*. [Orphaned-group hypothesis](https://marin-discord.pages.dev/#1364827114670657616/1392353824684900373) · [Stale-node explanation](https://marin-discord.pages.dev/#1364827114670657616/1392175683798831247) · [Failed-commit state](https://marin-discord.pages.dev/#1364827114670657616/1397293973474902127).

The head-node fix also needed revision. Setting head CPU to zero plus a custom status-actor resource helped on central1, where tokenization had previously landed on the head and caused OOMs. A stale deployment config separately produced an infeasible head-affinity error; later, the team questioned whether zero CPU was appropriate on central2 and discussed node-affinity scheduling instead. A head-pinned `run_on_pod_ray` experiment improved some preemption recovery but did not fully solve SliceActor creation timeouts. No single configuration was shown to settle all these cases. [Central1 improvement](https://marin-discord.pages.dev/#1391885957766058124/1391888700325236766) · [Stale config](https://marin-discord.pages.dev/#1364827114670657616/1389434790821888070) · [Central2 doubt](https://marin-discord.pages.dev/#1364827114670657616/1391885957766058124) · [Controller experiment](https://marin-discord.pages.dev/#1364827114670657616/1396310453981810759) · [Residual timeout](https://marin-discord.pages.dev/#1364827114670657616/1396331645975400529).

Capacity, setup, and package-state failures frequently looked alike to an experimenter staring at pending jobs. Preemptible *quota* did not guarantee available TPUs; a later GCP operation explicitly reported no v4 capacity in us-central2-b. For large slices, Ray's cap on simultaneous SSH setup connections combined with big Docker pulls made a slice take roughly 40 minutes when a simpler script finished in about five, suggesting setup concurrency rather than allocation alone. At another point, an expired container image, unavailable v4 capacity, and a half-completed `uv` migration all overlapped. The July `uv` rollout also exposed that a `uv` virtual environment need not include `pip`, while Ray's nested task setup still invoked `python -m pip`. Pinning a dependency in the local environment was no substitute for checking `pip freeze` *inside* Ray workers. [Capacity error](https://marin-discord.pages.dev/#1364827114670657616/1394552627320328283) · [SSH setup cap](https://marin-discord.pages.dev/#1364827114670657616/1396393628351463525) · [Compound outage](https://marin-discord.pages.dev/#1364827114670657616/1394360272059236576) · [Ray/uv boundary](https://marin-discord.pages.dev/#1364827114670657616/1392281220355723375) · [Remote version check](https://marin-discord.pages.dev/#1390865747999461548/1390866487505322035).

Device cleanup revealed why deleting a lock file is not equivalent to freeing a TPU. After a remote task raised, a Ray worker process could remain alive holding `/dev/accel*`; a retry then failed to initialize the device. Removing the team's separate lock file did not release the device handle. The developers traced the earlier process ID and considered explicit child-process lifetime management or discarding an unhealthy slice, with multi-user safety called out for any cleanup actor. A targeted hack reportedly fixed one reproduction, but the channel still debated the right abstraction. [File versus device](https://marin-discord.pages.dev/#1364827114670657616/1399861854456778816) · [Process-ID evidence](https://marin-discord.pages.dev/#1364827114670657616/1399951413605564418) · [Cleanup alternatives](https://marin-discord.pages.dev/#1364827114670657616/1400275171633401940) · [Targeted workaround](https://marin-discord.pages.dev/#1364827114670657616/1400531543851536525).

## August 2025: orchestration versus availability

August made the distinction between *allocated*, *registered*, and *usable* workers particularly concrete. Reserved TPU slices could appear in GCP yet not in Ray after a cluster restart; recovery involved reattaching workers and checking whether each worker's Docker process was alive and connected to the head. A worker-only reboot and a full cluster reboot were not interchangeable operations. The autoscaler also queried names of preempted GCP nodes and received 404s; in some cases it recovered without intervention, so those errors alone did not establish head-node OOM. [Reserved slices missing from Ray](https://marin-discord.pages.dev/#1364827114670657616/1403166384078327838) · [Worker connection diagnosis](https://marin-discord.pages.dev/#1403253739183145011/1403545893663408298) · [Stale-node queries](https://marin-discord.pages.dev/#1405592106151579730/1405660474426785862) · [Later recovery](https://marin-discord.pages.dev/#1364827114670657616/1407975828347682847).

Several apparently similar pending-job incidents had different causes. An expired pinned Docker image prevented one cluster restart; a fallback image and manual worker reattachment restored some service. On another day, workers failed registration because `RayParams.__init__()` rejected a `storage` argument, invalidating an initial head-memory guess. Late in the month, an expired image overlapped with actual shortage of spot v4 capacity. A rebuilt image addressed the artifact failure but did not by itself make the requested v4-128 available. The diagnostic sequence was to inspect the image ID and worker startup error, then separately check cloud allocation, quota, and Ray registration. [Expired-image restart](https://marin-discord.pages.dev/#1364827114670657616/1400946583645716551) · [Ray startup error](https://marin-discord.pages.dev/#1364827114670657616/1402054978121498745) · [Image versus capacity](https://marin-discord.pages.dev/#1409598000564670677/1409634074481524837) · [Remaining v4-128 issue](https://marin-discord.pages.dev/#1409598000564670677/1410023320535044259).

Evaluation exposed a process-lifetime problem as well as an observability gap. Participants suspected Evalchemy subprocesses left behind by failed parent jobs of keeping TPU devices locked; the Levanter fix under discussion covered training, not the evaluation path. They also wanted central logs because retries in the Ray dashboard could hide the previous attempt's logs, leaving head-node searches as the fallback. A GCS-backed logging path was proposed, not reported as complete. A separate checkpoint-resume failure claimed a path was missing although it existed in GCS; `discover_latest` was only a hypothesis, and a subsequent run did not reproduce the symptom. [Eval process suspicion](https://marin-discord.pages.dev/#1402056214929608844/1402088035935584346) · [Training/eval distinction](https://marin-discord.pages.dev/#1402056214929608844/1402122074662895678) · [Retry log loss](https://marin-discord.pages.dev/#1402071962775322705/1402072244330430524) · [Checkpoint uncertainty](https://marin-discord.pages.dev/#1407592622561955841/1407610064868479016).

The cooldown-mixture discussion showed that a scheduled data-mix change cannot always occur at an arbitrary optimizer step. The sequence index was calculated as `batch_size * step` and had to align to a mixture block size; with batch size 16 and block size 2,048, legal boundaries were multiples of 128 steps. When both batch size and mixture changed in a later 32B schedule, there was no suitable boundary without a temporary adjustment. A workaround was discussed, but the durable lesson is to check data-assignment granularity before promising a training-stage boundary. [Alignment rule](https://marin-discord.pages.dev/#1407228975461433414/1407238501971263649) · [Schedule conflict](https://marin-discord.pages.dev/#1407228975461433414/1409758309099245570) · [Workaround discussion](https://marin-discord.pages.dev/#1407228975461433414/1409758706077405236).

Finally, resource cleanup had a social as well as technical boundary. Teams inventoried rarely used clusters competing for v4 quota, sought owners' consent before removing them, and considered v4-64 where v4-128 was scarce. A cluster taken down without checking with its user prompted an explicit request to coordinate first. The August reliability agenda similarly called for crash alerts independent of W&B, preemption cleanup, Docker image retention, and repeatable manual-worker reattachment. These are practices for shared infrastructure, not proof that any one patch solved availability. [Quota inventory](https://marin-discord.pages.dev/#1364827114670657616/1410330644290080890) · [Owner coordination](https://marin-discord.pages.dev/#1409598000564670677/1410307692672712744) · [Smaller-slice option](https://marin-discord.pages.dev/#1364827114670657616/1410357738869096559) · [Reliability agenda](https://marin-discord.pages.dev/#1364827114670657616/1409642552960880780).

## September 2025: runtime environments and shared-cluster limits

The September Ray-version incident showed that a project pin is not enough when nested runtime setup has multiple installation paths. An evaluator worker loaded Ray 2.49.1 into an environment whose cluster Ray was 2.45.0, and Ray refused the version change. The team found a second dependency installer in the executor that did not apply the same Ray filtering as `ray_run`; the evaluation helpers also specified their own Levanter and pip packages. Removing Dolma fixed one dependency conflict but **not** the Ray error. Dolma itself had old `fsspec` and Rust-build constraints, so contributors pushed it toward an optional, isolated dependency rather than forcing every job through a Cargo build. A later pending-job episode was traced to that silent build during environment setup. [Ray mismatch](https://marin-discord.pages.dev/#1364827114670657616/1413438431417340016) · [Second install path](https://marin-discord.pages.dev/#1364827114670657616/1413587911575732285) · [Separate Dolma failure](https://marin-discord.pages.dev/#1364827114670657616/1413610963944603710) · [Dolma isolation](https://marin-discord.pages.dev/#1364827114670657616/1413591888308731936) · [Silent Cargo setup](https://marin-discord.pages.dev/#1364827114670657616/1414703314850807889).

The JAX/PJRT failures sharpened the distinction between the local, cluster-image, and per-job dependency sets. JAX 0.7.2 worked when invoked directly in one container but crashed through a Ray job in `WatchGlobalProcessInfo`; pinning JAX 0.6.2 in the job and rebuilding the cluster image was the immediate workaround. A later worker still showed mutually conditional JAX 0.6.2 and 0.7.2 dependencies, and the missing TPU extra was suspected because it would omit the intended JAX/libtpu pairing. Merging main, syncing the environment, and verifying the actual worker versions got one run progressing, but another September 30 case still failed with a suspected incompatible libtpu. The archive does not establish one universal root cause for every PJRT crash. [Ray versus direct run](https://marin-discord.pages.dev/#1364827114670657616/1419834058933932234) · [0.6.2 workaround](https://marin-discord.pages.dev/#1364827114670657616/1419827892820512900) · [Conflicting resolved versions](https://marin-discord.pages.dev/#1364827114670657616/1420171715379462274) · [Successful sync](https://marin-discord.pages.dev/#1364827114670657616/1420183812155117738) · [Remaining libtpu hypothesis](https://marin-discord.pages.dev/#1422636764702572709/1422672733396795583).

TPU slice-join timeouts were also not necessarily hardware failures. A v5-128 slice exposed 32 VMs while Levanter waited for only 16 actors because its host-count arithmetic assumed the wrong mapping of cores, chips, hosts, and VMs. A quick correction exposed the converse error for v4-128, whose 128 cores corresponded to 16 hosts in that discussion. Ray's reported chips-per-host could be correct yet still be the wrong quantity for scheduling actors; v5litepod and v6e layouts differed again. The group moved toward architecture-specific counts rather than treating the first formula as universal. [v5 actor mismatch](https://marin-discord.pages.dev/#1364827114670657616/1416211871354327081) · [v4 counterexample](https://marin-discord.pages.dev/#1364827114670657616/1418757367109128265) · [VM-versus-host correction](https://marin-discord.pages.dev/#1364827114670657616/1420263008533352509) · [Architecture-specific fix](https://marin-discord.pages.dev/#1364827114670657616/1420527290869092404).

Running hundreds of sweep jobs against a shared cluster with roughly ten nodes could monopolize the Ray queue, delaying short evaluations and debugging even when each job correctly requested resources. The immediate practice was backpressure: submit only a small number of concurrent jobs, using an existing runtime helper or chunked `executor_main` calls. This did not guarantee debugger access if multiple users swept simultaneously. Participants discussed a dedicated reserved-capacity debug cluster, but separate autoscaling clusters in a region would still compete for the same preemptible quota; genuine priority queues or another scheduler remained a design question. [Sweep warning](https://marin-discord.pages.dev/#1364827114670657616/1417106112146047017) · [Existing backpressure helper](https://marin-discord.pages.dev/#1417106831632896074/1417196453658361956) · [Debug-capacity trade-off](https://marin-discord.pages.dev/#1364827114670657616/1417288664152543273) · [Scheduler debate](https://marin-discord.pages.dev/#1417295718506303548/1417297643738103902).

Several observability failures made symptoms look broader than they were. Ray autoscaler warnings from one user's invalid resource request appeared in everyone else's logs; `ray exec` reached the *head*, whereas failed-worker logs lived on the worker. The useful path was to take the IP from the job error, map it to a TPU VM, and inspect that node's `/tmp/ray/session_latest/logs`; even that could fail after preemption. A diagnostic script initially used a region where `gcloud` required a zone, producing a misleading permission/not-found error. Tools to SSH by IP and reserve an interactive development TPU reduced this friction but did not make the logs durable. [Shared-warning ambiguity](https://marin-discord.pages.dev/#1418714372032954419/1418716486544916521) · [Head versus worker logs](https://marin-discord.pages.dev/#1417721314076135424/1417738756563271680) · [Region/zone bug](https://marin-discord.pages.dev/#1417721314076135424/1417743225082613770) · [Preempted evidence loss](https://marin-discord.pages.dev/#1417721314076135424/1417753156309225492) · [Development TPU workflow](https://marin-discord.pages.dev/#1364827114670657616/1418274519352869045).

Disk and device ownership remained distinct hazards. A failed job could leave downloads in `/tmp` with no clean-up path, filling a worker so even a Cargo build failed. A September inspection found roughly 50 GB of Hugging Face cache inside one Docker layer; moving `HF_HOME` to shared memory was proposed, but checkpoints could then fill that memory instead. In another case, an idle Ray worker process still held a TPU file descriptor; a cleanup actor that Ray scheduled only on apparently free TPU resources was experimental and had to avoid killing live training. For 32B evaluation, downloading the model to local `/tmp` was too large for the current worker disk, with a GCSFuse cache path proposed as a workaround. [Crash-left scratch data](https://marin-discord.pages.dev/#1364827114670657616/1413675893594914928) · [HF cache measurement](https://marin-discord.pages.dev/#1364827114670657616/1418300504559321130) · [Shared-memory caveat](https://marin-discord.pages.dev/#1364827114670657616/1418301058127626411) · [Idle Ray process holding TPU](https://marin-discord.pages.dev/#1364827114670657616/1415776212533510335) · [Experimental cleanup](https://marin-discord.pages.dev/#1364827114670657616/1415818737709486252) · [Large-model cache workaround](https://marin-discord.pages.dev/#1417321874563792967/1417322184983973989).

Finally, small interface assumptions repeatedly broke worker recovery. Ray added Docker `--rm`, conflicting with the proposed `--restart` flag; a gcloud text-format change made case-sensitive `networkIp` parsing miss the head address, and a later broad cluster-name filter found *multiple* head IPs. After updating the init script, one operator reattached a reserved worker without reprovisioning its TPU. The same month exposed a hidden evaluation dependency: `datasets>=4` no longer ran the dataset script needed by a Winograd task, but the top-level error misleadingly named `num_fewshot`. The reported temporary pin was `datasets==3.6.0`; it was not a general fix for evaluation compatibility. [Docker flag conflict](https://marin-discord.pages.dev/#1364827114670657616/1418643618515779725) · [Head-IP parse](https://marin-discord.pages.dev/#1364827114670657616/1418718319615283380) · [Multiple-head match](https://marin-discord.pages.dev/#1364827114670657616/1421228412730867753) · [Reattachment](https://marin-discord.pages.dev/#1364827114670657616/1421230797310005258) · [Underlying dataset error](https://marin-discord.pages.dev/#1418664908756746331/1418665372432859228) · [Temporary pin](https://marin-discord.pages.dev/#1418664908756746331/1418665503546671115).

## October 2025: distinguish capacity, placement, and correctness

An October 32B evaluation investigation corrected a plausible but incomplete storage diagnosis. Logs showed a checkpoint downloaded under `/dev/shm/levanter-lm-eval` while cleanup removed `/tmp/huggingface-cache`, a real path mismatch. But when the user entered the *container*, the evaluation cache was empty and its `/dev/shm` mount was only 32 GB—too small for that single model. The host's larger shared-memory mount was not the container's limit. GCSFuse was used for other 32B evaluations; pointing this path there or enlarging the container mount was discussed, with cache locality and load time as separate concerns. Thus “no space” required inspecting the exact path, mount namespace, and model size before attributing it to leaked prior runs. [Mismatched cleanup paths](https://marin-discord.pages.dev/#1422607680253464616/1423022712850350231) · [Empty container cache](https://marin-discord.pages.dev/#1422607680253464616/1423032051929710622) · [32 GB mount](https://marin-discord.pages.dev/#1422607680253464616/1423032617313243189) · [GCSFuse alternative](https://marin-discord.pages.dev/#1422607680253464616/1423033817110806638).

The TPU availability discussions kept three different states apart: quota is the team's allowance, cloud capacity is what Google can allocate in a zone, and Ray's dashboard is its own sometimes-stale view of registered resources. A v6e request repeatedly created and failed without ever reaching `PREEMPTED`; a direct GCP create call returned “insufficient capacity.” Preemption means an already-held node was taken away. Elsewhere, a cluster head actually died, while another had no accelerator supply despite a live head. The new multi-cluster dashboard made these states easier to compare but was not a guarantee of real allocatable capacity. [Capacity versus preemption](https://marin-discord.pages.dev/#1422709549705461810/1422710935470084106) · [Quota versus capacity](https://marin-discord.pages.dev/#1364827114670657616/1424164769296027668) · [Dead head](https://marin-discord.pages.dev/#1364827114670657616/1423464619757932556) · [Cloud versus Ray view](https://marin-discord.pages.dev/#1364827114670657616/1429605171926929499) · [Multi-cluster view](https://marin-discord.pages.dev/#1364827114670657616/1423757442398814339).

The mesh debugging exchange gave a more precise interpretation than “add a mesh context manager.” An error with the *same* TPU device IDs in a different order meant an array had likely been created using the default mesh while the JIT used the intended context mesh; the suggested remedies were to create the array within the JIT or use `make_array_from_callback`. A CPU JIT receiving a TPU array was a different category, to handle by moving the value to the CPU before that function. In one case `broadcast_one_to_all` created an array without respecting the context mesh, while the JIT did respect it; Levanter's replacement helpers were proposed for Haliax. The claimed workaround initially still showed an intermittent failure, so the message is a diagnostic model, not a blanket assertion that the bug was gone. [Two error categories](https://marin-discord.pages.dev/#1364827114670657616/1425194756404809798) · [Broadcast/JIT mismatch](https://marin-discord.pages.dev/#1364827114670657616/1425193399748657193) · [Intermittent follow-up](https://marin-discord.pages.dev/#1364827114670657616/1425192906834317333).

TPU device-busy reports again showed that a scheduler request is not the only way to touch an accelerator. Using `jnp.logspace` in a launcher to build sweep parameters caused JAX to initialize the TPU on a machine even though that launch task had requested no TPU; a separate actor's `jax.random` call had the same suspected effect. Those cases differed from an idle Ray worker retaining a device handle. Checking which process held `/dev/vfio/0` was suggested before killing a node. Cleanup of preempted nodes later became a `cluster.py run-cleanup` operation, but cleaning stale device locks on *live* multi-host slices remained a separate, harder problem. ## November 2025: reproducible data paths and reusable workers

Versioned experiment inputs behave like a dependency tree: changing an input path can change the version hash and invalidate downstream caches even if the bytes were merely relocated to another region. The discussion identified `versioned("gs://...")` on hard-coded input paths as a pattern to avoid. `InputName.hard_coded` was named as an escape hatch, while `override_output_path` could deliberately retain a derived artifact's identity; both require care because pinning identity can hide stale data. This matters for a future regional data-cache layer: physical placement and logical dataset identity cannot be casually conflated. [Path/version question](https://marin-discord.pages.dev/#1364827114670657616/1434950832566177863) · [Hard-coded input guidance](https://marin-discord.pages.dev/#1364827114670657616/1434951734890856539) · [Dependency-tree consequence](https://marin-discord.pages.dev/#1364827114670657616/1434952209392599130) · [Output-path override](https://marin-discord.pages.dev/#1364827114670657616/1434952660661960977).

Evaluation granularity was a cost and throughput decision, not just a clean API choice. A workflow with one job per model–book pair repeatedly lost the GCSFuse cache when another user's job occupied the worker; reloading Llama 70B then took 10–15 minutes per job rather than under 30 seconds from a warm cache. With thousands of books, the group favored doing more books per model invocation or using persistent workers that load the model once and receive examples. A proposed worker pool would manage device-backed workers, while fsspec checkpoint reads might shorten cold loads but had not eliminated the architectural problem. ## December 2025: state compatibility across clusters and data pipelines

The most consequential cluster-startup investigation uncovered *two* kinds of version contamination. A central2 head ran Ray 2.49 from a Docker base image while the uv lock specified 2.45; changing one config did not fix startup, and a known image with Ray 2.45 brought the head back. Then operators found workers still running the older `marin-demo` image: their startup script searched for the regional `marin-us-central2` head, so those demo workers joined the production cluster despite a successful restart with the correct config. The lesson is to verify the running image and package versions on both head and workers, plus the discovery labels that determine which cluster each worker joins. A restart alone did not isolate the cluster. ## Reliability and scheduling

Most posts are transient job reports, but the recurring problem is reproducible training on preemptible, distributed accelerators. In 2025, Ray worker pressure, lost manual workers, and head-node failures repeatedly interrupted jobs. One run encountered 64 workers killed for memory pressure; another experiment tried pinning `run_on_pod_ray` to the head node so preemption recovery would be less fragile. The team's August reliability list called for explicit crash alerts independent of W&B, better worker reattachment, preempted-node cleanup, and retention of container images needed to restart clusters. [Worker pressure](https://marin-discord.pages.dev/#1364827114670657616/1370904887558275173); [preemption experiment](https://marin-discord.pages.dev/#1364827114670657616/1396310453981810759); [reliability agenda](https://marin-discord.pages.dev/#1364827114670657616/1409642552960880780).

That reliability problem had several independent layers. One July 2025 outage combined an expired container image, v4 TPU provisioning trouble, and a broken build during an incomplete `uv` migration. A training or evaluation failure could therefore be an artifact-availability, cluster-capacity, or dependency problem rather than one defect with one fix. GPU/TPU dependency resolution had its own failure mode: an upper bound in one package led the solver to an older version without that bound, then to a chain of incompatible old dependencies. The reported remedy was to refine pins incrementally. [Compound outage](https://marin-discord.pages.dev/#1364827114670657616/1394360272059236576); [dependency-solver mechanism](https://marin-discord.pages.dev/#1364827114670657616/1435754744596529163).

The Ray clusters moved to token authentication in January 2026 after security concerns about remote-code-execution exposure. The migration required a reboot, interruption planning, and fresh client authentication; running experiments needed checkpoints and resubmission plans. By February, Iris offered a region-aware `iris job run` path that could schedule across zones and removed some manually chosen storage-prefix settings. Iris itself still had a restart and state-recovery learning curve: a March controller restart lost state and required database recovery. These messages document a transition, not a claim that the new orchestrator had no failures. [Ray migration](https://marin-discord.pages.dev/#1364827114670657616/1456402718481711337); [Iris beta](https://marin-discord.pages.dev/#1364827114670657616/1476412061339619469); [controller recovery](https://marin-discord.pages.dev/#1364827114670657616/1486408175266824432).

Iris made job and log links shareable through a hosted dashboard, reducing dependence on local port forwarding. That improved collaborative diagnosis, but the group still had to separate controller, package setup, job, and training failures. A July vLLM-worker startup problem, for example, was a 300-second lock timeout while multiple workers fetched a Git dependency; it was not evidence that the model or inference kernel was broken. [Dashboard](https://marin-discord.pages.dev/#1364827114670657616/1493692493374554293); [dependency lock](https://marin-discord.pages.dev/#1364827114670657616/1525035072414023750).

Iris reservations tried to remove the burden of locating a free TPU slice: a job could request a device type, wait for allocation, and place child jobs in the allocated region. The March 2026 announcement warned that multiple reservations were not yet constrained to one region and that the data prefix should follow the selected region. A later autoscaler discussion proposed that equal-priority scale groups were chosen by configuration order rather than available capacity; the cited message is a diagnosis and proposed fix, not confirmation that this was the sole cause or that it had shipped. [Reservation behavior and caveat](https://marin-discord.pages.dev/#1364827114670657616/1478098597344973013); [autoscaler diagnosis](https://marin-discord.pages.dev/#1481718488748785664/1481775706458292295).

## Evaluation, artifacts, and cost

An evaluation job could appear to fail for reasons unrelated to the model. In October 2025, checkpoint-download and cleanup paths differed, but follow-up found an empty cache and a container shared-memory mount too small for one 32B model; see the October section above. A February 2026 Evalchemy integration moved evaluation in-process, fixed bugs, and reported roughly 10x speedup; orphaned subprocesses had been keeping TPU devices locked after their parent died. Another investigation found that memray's failure to compress a profiler file was not the cause of task failures: the actual failures included benchmark-loading errors. The general diagnostic practice is to trace a symptom to the failing process, data path, and task outcome before changing training code. [Cache-path and capacity follow-up](https://marin-discord.pages.dev/#1422607680253464616/1423032617313243189); [Evalchemy update](https://marin-discord.pages.dev/#1364827114670657616/1471664293479972886); [profiler false lead](https://marin-discord.pages.dev/#1364827114670657616/1491210597172252762).

The team also considered narrowing *in-training* evaluation to a robust signal such as MMLU after CORE task downloads repeatedly killed annealing jobs, then running specialized benchmarks after training. That was a proposal to separate training liveness from breadth of evaluation, not an assertion that MMLU alone is sufficient. TPU CI had a related coverage trade-off: it ran only for explicit labels or selected paths, so changes outside the path list could break TPU behavior without a test firing. [Annealing-eval proposal](https://marin-discord.pages.dev/#1364827114670657616/1372317550075187312); [TPU CI trigger policy](https://marin-discord.pages.dev/#1364827114670657616/1367262649653661757).

Serving needed correctness checks under realistic load, not only startup and throughput checks. A June 2026 report said a vLLM TPU configuration using PyTorch/XLA with data parallelism above one generated corrupted or repetitive output increasingly under load. The reported lesson was to inspect traces and output quality before trusting an apparently live service; the Discord post did not establish a general failure of all vLLM-on-TPU configurations. [Load-dependent decode report](https://marin-discord.pages.dev/#1364827114670657616/1511756705468514325).

Checkpoint storage was estimated at roughly $60,000 per month. The ensuing retention debate exposed a real research trade-off: deleting checkpoints after one month would cut cost but could remove baselines needed for three- to six-month comparisons. A warning, ownership, and recovery policy was still under discussion in the cited exchange. The same resource-awareness appears in plans to use Parquet consistently and to cache tokenizers and dependency artifacts instead of repeating costly setup work. [Storage estimate](https://marin-discord.pages.dev/#1364827114670657616/1490767485547319388); [retention concern](https://marin-discord.pages.dev/#1364827114670657616/1490771304188481657); [tokenizer cache proposal](https://marin-discord.pages.dev/#1464369718457798819/1464445011503611957).

Placement and artifact size were operational costs too. A February 2026 warning said cross-region data reads were incurring more than $1,000 per day, so keeping compute near its input data mattered even when another region had available TPUs. Some workers lacked the 32 GB of free local disk needed to fetch what appeared to be an 8 GB model, illustrating that compressed model size was not a safe disk-capacity estimate. ## Reproducibility and access

Code and package state were recurrent experimental variables. A developer found that `ray_run.py` had read environment variables from another worktree, silently overriding a launch configuration. A later vLLM-TPU fork proposal required CI-built wheels, a versioned dependency, and a separately maintained fork rather than an untracked local build. These details affect whether someone else can rerun the same experiment. [Worktree configuration failure](https://marin-discord.pages.dev/#1364827114670657616/1403127593732931706); [fork packaging requirements](https://marin-discord.pages.dev/#1364827114670657616/1484638373128699986).

Version changes could alter the scientific budget itself: one user reported that moving from JAX 0.6.2 to 0.8.0 raised compile-time memory enough to halve the batch size that fit, from 128 to 64. For long-running hero jobs, a two-week Iris branch-age limit created a different tension: restarting after hardware failure could require pulling many unrelated main-branch changes mid-run. The discussion asked whether a pinned exception or selective updates would be safer; it did not settle a universal policy. An April 2026 audit said a beginning-of-sequence tokenizer bug had affected several tokenized corpora, including SWE-ZERO and protein documents, and prompted requests to delete or re-tokenize affected caches. The affected-set list was partly inferred by an agent and was still being checked with owners in the cited post; it should not be treated as a final inventory. [Tokenizer-cache audit](https://marin-discord.pages.dev/#1364827114670657616/1497036970851963113).

The group debated whether the experiment executor was formalizing scientific protocols or imposing maintenance overhead without delivering that benefit. A formal, runnable protocol could preserve decisions that a final-run report omits, especially for agent-led research. In practice, participants questioned whether executor code captured the protocol at all; one proposed retaining reproducible data preparation and named output artifacts while simplifying the model-training pipeline. This was an architectural debate, not a completed removal. [Protocol rationale and concern](https://marin-discord.pages.dev/#1364827114670657616/1519443077926748311); [data-cache versus model-pipeline distinction](https://marin-discord.pages.dev/#1364827114670657616/1519686532057927751).

Opening the platform to more contributors raised an access-control question: Iris did not yet strongly sandbox a limited-trust user from running arbitrary expensive code. Separately, attempts to use Marin models outside the monorepo showed how much implicit documentation and model setup agents depended on. These remained design and documentation needs, not solved operational properties.
