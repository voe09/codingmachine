# #zephyr

Archive coverage: 2025-11-11–2026-02-19 (UTC); 145 messages, including 12 thread replies. Every exported message body was reviewed chronologically. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1437693140470464552).

Zephyr was introduced as a dataflow processor to replace a collection of older data-processing paths, roughly in the space of Beam or Ray Data. It could read JSONL or Parquet and write Parquet, but adopting Parquet as the common stored format was still a separate objective. Its initial deduplication primitive had not been tested at scale. The discussion distinguished exact hashing from fuzzy simhash/LSH-style deduplication: softness may be useful for near-duplicate training text, while train/test overlap can require a more exact criterion. A proposed scalable shape was to compute duplicate IDs, repartition the survivors, and join them back to full documents; GCS spilling might be necessary because Ray's default local-disk spill target was smaller than available RAM in that environment. These were design directions, not proof of a production-scale dedup pass. Fault tolerance turned on where progress was persisted. Zephyr could retry a preempted Ray task, and `skip_existing_outputs=True` avoided redoing *completed* output shards after a rerun. It did not resume a partially written shard from its `.tmp` files: each shard was all-or-nothing. For expensive per-document API calls, a user could lower the work lost to preemption by selecting a small `chunk_size`, reshuffling into roughly `total_records / chunk_size` shards, then mapping the API call. The tradeoff was thousands of small outputs; reshuffling back to fewer files before writing relied on Ray's in-flight recovery rather than durable GCS checkpoints, while writing small completed shards first and compacting them in a separate pipeline retained durable progress. `flow_backend` selected a thread pool locally and Ray on the cluster. The Levanter token-cache migration exposed a subtler output-contract issue. Fusion meant the tokenizer did *not* hold a multi-terabyte dataset in Ray's object store: each input group could be tokenized and written independently. But writing independent `part-*` TreeStore caches was not yet equivalent to one final Levanter cache. The old flow wrote temporary shard caches, concatenated their token arrays in order into a final cache, then removed the temporaries; the concatenation was close to large memory copies, not re-tokenization. The new writer was not append-mode, so simply skipping finished parts could not by itself produce a correct single final array. An early training test still showed decreasing loss, yet a later trainer saw zero-length data because shard offsets were wrong. That is why output shape, offsets, shard coverage, and resumption need tests beyond “the model trains.” A runtime `ShardedDataSource` or virtual view was considered, but random-access requirements made it nontrivial. Two API details could silently change semantics. MessagePack serialization did not round-trip dataclasses as dataclasses in ported pipelines, prompting a pickle fallback rather than an expensive object-graph inspection before every serialization. `execute()` was changed from a lazy iterator to an eager list because constructing a pipeline without consuming the iterator had meant the work never ran at all. For sampling, `take_by_shard(10)` over ten equally sized source files takes ten items *per file*, about 100 total—not ten from the whole dataset; a global `take()` was discussed but would complicate JSONL fusion. These are small interface choices with large effects on whether a dataset is correctly produced.
