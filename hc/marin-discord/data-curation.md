# #data-curation

Archive coverage: 2025-05-15–2026-09-22 (UTC); 903 messages, including 390 thread replies. Every exported message body and thread reply was reviewed chronologically. Seven attachment-only posts had no text to evaluate, and linked external artifacts were not independently audited. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1368297424086499359).

## Provenance, licenses, and release hygiene

The first release discussion insisted on a separate data card for each corpus, linked from the model card. The team also had to account for Wikimedia stopping replication of its experimental Enterprise HTML mirrors in March 2025; future HTML Wikipedia processing would need ordinary dumps unless the March mirror survived. Hugging Face flagged apparent secrets inside uploaded data. The conversation identified them as likely third-party secrets already present on the public web and discussed masking, but did not record a completed remediation. [Data cards](https://marin-discord.pages.dev/#1368297424086499359/1373033396997193890); [Wikimedia mirror](https://marin-discord.pages.dev/#1368297424086499359/1373017231977611266); [secret warning](https://marin-discord.pages.dev/#1368297424086499359/1373350989679038495).

The proposed Nemotron-CC v2 upgrade was stopped in discussion by its dataset license, which restricted use and disclosure of dataset benchmark results. The archive does not show a negotiated resolution. Later, contributors again questioned whether Nemotron pretraining-data terms met open-data goals, even while noting that released Nemotron collections had been ingested. Availability and suitability for an open-science release were separate questions. [License excerpt](https://marin-discord.pages.dev/#1368297424086499359/1436067847519604847); [later concern](https://marin-discord.pages.dev/#1505202592966512843/1505915489866743889).

## Code data: inspect shards and resource use

For a Marin 32B cooldown, participants wanted stronger code data than StarCoder and considered Stack v2, a Common Pile educationally filtered Stack v2 subset, and MegaMath for math. The Hugging Face preview of the filtered code set looked nearly all Markdown and initially prompted a harsh quality assessment. Reading later shards revealed PHP and Python; the preview exposed only an early, file-type-ordered slice. The team built a Python filter and scheduled the cooldown to switch to a mix containing that slice. A dataset viewer's first rows were not representative of its full contents. [Cooldown proposal](https://marin-discord.pages.dev/#1368297424086499359/1426310963791003789); [preview concern](https://marin-discord.pages.dev/#1368297424086499359/1426323721815330957); [later-shard check](https://marin-discord.pages.dev/#1368297424086499359/1426332930820669613); [mix switch](https://marin-discord.pages.dev/#1368297424086499359/1426371124639567924).

Tokenizing Stack v2 then hit Ray node memory limits. A task log showed four tokenization workers using roughly 86–93 GB each on the same 441 GB node, alongside a 47 GB training process; the node crossed Ray's 95% threshold. The diagnosis was aggregate co-location pressure. Increasing each tokenization task's CPU reservation was proposed to spread them across nodes; the relevant request lived in Levanter, not the Iris entrypoint CPU flag. The archive records advice and an intent to retry, not a final outcome. [OOM log](https://marin-discord.pages.dev/#1429929633058656466/1429935278398898307); [diagnosis](https://marin-discord.pages.dev/#1429929633058656466/1429939014600888390); [resource setting](https://marin-discord.pages.dev/#1429929633058656466/1429944319699189803).

When Stack v3 arrived in July 2026, the intended replacement was broader than adding another source: participants wanted to remove CommonPile Stack v2 and possibly Dolma 3.5 code derived from v2 to avoid retaining redundant older material. Downloading, token counting, and staging were still underway. [Replacement discussion](https://marin-discord.pages.dev/#1368297424086499359/1529894190077710387); [staging update](https://marin-discord.pages.dev/#1368297424086499359/1530031290034815096).

## Rewriting open text

A SwallowCode/SwallowMath paper prompted interest because it reported gains from rewritten domain data under a fixed 50B-token training budget. Marin contributors raised two qualifications: rewriting consumes compute that could train longer, and an internal trial of the paper's code data did not substantially improve their training. That local result was for code; the math variant was not tried in the exchange. [Paper results quoted in Discord](https://marin-discord.pages.dev/#1368297424086499359/1385002214044467250); [compute objection](https://marin-discord.pages.dev/#1368297424086499359/1385003698606051358); [local code result](https://marin-discord.pages.dev/#1368297424086499359/1385309491079417957).

An open-data collaboration proposed rewriting openly licensed source text, initially a few hundred billion tokens for a controlled small-model comparison and eventually about 4–5T tokens. It avoided unconstrained synthetic generation because a teacher might reproduce copyrighted training text. Patent applications illustrated another goal: retain some raw format knowledge while turning formulaic content into denser natural language. Different patents can carry different facts despite shared boilerplate, so rewriting was distinguished from deduplication. Participants proposed comparing rewritten-only text with original-plus-rewrite pairs; no result for that ablation appears here. Qwen3-4B was suggested on cost and spot-checked quality grounds, except perhaps for code. The 5T figure was an ambition, not an assembled corpus. [Proposal](https://marin-discord.pages.dev/#1368297424086499359/1437529815665213480); [copyright rationale](https://marin-discord.pages.dev/#1368297424086499359/1437931877494161489); [patent debate](https://marin-discord.pages.dev/#1368297424086499359/1438090379839799297); [pairing ablation](https://marin-discord.pages.dev/#1368297424086499359/1438207959359422657); [initial scale](https://marin-discord.pages.dev/#1368297424086499359/1438564589846528142).

Formatting diversity became another question. Marin 8B was reported sensitive to paragraph newline counts and residual HTML entities such as `&gt;`; one hypothesis was that a small fraction of raw HTML, extracted HTML, and varied paragraph renderings could reduce brittleness. A reply suggested vocabulary normalization as another possible cause and remedy. The thread ended with a shift of immediate attention toward reformatting FLAN examples, so HTML augmentation remained untested here. [Formatting sensitivity](https://marin-discord.pages.dev/#1368297424086499359/1509063908894310520); [vocabulary alternative](https://marin-discord.pages.dev/#1368297424086499359/1509090916269424722); [changed priority](https://marin-discord.pages.dev/#1368297424086499359/1509224574406098975).

## OpenThoughts4: length, format, and generation failures

Marin and LAION coordinated OpenThoughts4 generation across math, code, and science. Marin's initial Qwen3-32B annotations capped outputs at about 7.5k tokens. LAION reported spending 150,000 H100 hours on a 32k-output code set. The teams proposed controlled teacher and trace-length comparisons. They also had to convert generated columns into the `conversations` format expected by existing post-training code; the converted 7k code set was published, while math and science conversions were requested. [Generation report](https://marin-discord.pages.dev/#1368297424086499359/1446386279913750681); [format correction](https://marin-discord.pages.dev/#1368297424086499359/1451670823529353216); [converted code](https://marin-discord.pages.dev/#1368297424086499359/1451565620767363164).

The first 7.5k-versus-32k code comparison did not settle the length question. A Qwen3-1.7B student saw about 60–64B training tokens in each arm, requiring eight epochs of the shorter set versus two of the longer set. The 32k arm won on HumanEval, MBPP, and CodeForces; the 7.5k arm won on LiveCodeBench. Both fine-tuned models substantially underperformed their starting model. The author therefore treated the runs as inconclusive, with possible confounds from the recipe and code-only data. A later audit found roughly 90% of 7.5k math generations at the cap and about 12% of 32k math generations still truncated; completion rate alone did not establish downstream value. [Mixed results and setup](https://marin-discord.pages.dev/#1368297424086499359/1453511233255768145); [7.5k distribution](https://marin-discord.pages.dev/#1461252391570768036/1463627357226274988); [32k truncation](https://marin-discord.pages.dev/#1461252391570768036/1463643515677446328).

In January, Marin prepared matched 30k-prompt subsets for math, code, and science, each with Qwen3-32B generations capped at 32,768 tokens. Unique prompt IDs mattered because OpenThoughts4 contained repeated questions. Six training configurations compared 7,168, 16,384, and 32,768-token lengths on Qwen2.5-7B-Instruct and Qwen3-8B students. The shorter arms truncate the *same* 32k generations, testing the value of retaining later tokens. The channel links the configurations but gives no final result for the full six-run comparison. [Dataset and runs](https://marin-discord.pages.dev/#1461252391570768036/1463313310693855384); [paired construction](https://marin-discord.pages.dev/#1461252391570768036/1463348302836666533); [truncation design](https://marin-discord.pages.dev/#1461252391570768036/1463396632501420095).

A more serious issue emerged in the LAION 32k code release. A spot check found that the designated Qwen annotation column often lacked thinking traces and contained text resembling prompt continuation. The separate `output` column was inherited from the parent dataset and was not the new Qwen3-32B generation. LAION acknowledged widespread bad samples and considered regenerating the code portion; Marin generated its own 30k-code subset. Earlier training on the suspect LAION data cannot cleanly answer the trace-length question. The precise cause remained unresolved. [Column audit](https://marin-discord.pages.dev/#1461252391570768036/1461428623709044868); [quality acknowledgment](https://marin-discord.pages.dev/#1461252391570768036/1462076749310464124); [replacement subset](https://marin-discord.pages.dev/#1461252391570768036/1462221217611382814).

The May inventory exposed another scale problem: about 4.87M OpenThoughts4 rows represented only 253,926 unique prompts, with about 16 repeats per math and science seed and 105 per code seed. About 98% of OpenThoughts3's 65,080 unique prompts were also in OpenThoughts4; the latter had roughly 190k additional unique prompts. Contributors questioned whether spending a proposed 600,000 H100-hour budget on more annotations of repeated seeds was preferable to expanding seed diversity or agentic data. No final allocation decision appears here. [Row and seed counts](https://marin-discord.pages.dev/#1368297424086499359/1504818214025039992); [overlap](https://marin-discord.pages.dev/#1368297424086499359/1504818189064994896); [compute proposal](https://marin-discord.pages.dev/#1368297424086499359/1504633263984214036).

## Teacher quality depends on the student and answers

On 30,000 matched OpenThoughts4 math prompts, Qwen3-32B and Qwen3-235B-A22B provided separate 16k-cap responses for the same Qwen2.5-7B-Instruct student. The smaller teacher's annotations fit faster and its student scored higher on AIME. At ten epochs, reported AIME 2024/2025 scores were 36.7/36.7 for the 32B teacher and 33.3/23.3 for the 235B teacher. The comparison controlled prompts and training hyperparameters; it did not show that 32B was generally the stronger teacher. Contributors raised teacher–student distribution mismatch and overfitting as possible explanations. [Setup](https://marin-discord.pages.dev/#1368297424086499359/1459274785245626460); [scores](https://marin-discord.pages.dev/#1368297424086499359/1459339926058307594); [mismatch hypothesis](https://marin-discord.pages.dev/#1368297424086499359/1459275385312116746).

Follow-up experiments kept the 32B advantage with a long-context Marin 8B student. When both teachers produced the same final answer, their different reasoning traces trained students to roughly similar outcomes. The performance gap appeared chiefly where teachers disagreed, although OpenThoughts4 questions lacked ground-truth solutions to identify which answer was correct. Samples where one or both teachers never reached a final answer were excluded. Answer correctness and student fit remained entangled. [Follow-up](https://marin-discord.pages.dev/#1368297424086499359/1463233013130461346); [subset definitions](https://marin-discord.pages.dev/#1368297424086499359/1463234756513890457); [missing ground truth](https://marin-discord.pages.dev/#1463244982092693669/1463257951883100324).

A rejection-sampling test combined two teachers without a reward model. For a Qwen3-1.7B-Base student, eight responses from Qwen3-4B were sampled and one whose final answer matched a Qwen3-32B response was retained. This selected set modestly outperformed training on a random 4B response or directly on 32B responses in that setup. The verifier looked only at the final answer, so a flawed reasoning trace could still pass. Participants proposed richer reward models and a teacher–student–token-budget matrix with intrinsic fit measures; these remained research directions. [Result](https://marin-discord.pages.dev/#1368297424086499359/1476381841345744961); [limitation](https://marin-discord.pages.dev/#1368297424086499359/1476404328192544799); [comparison proposal](https://marin-discord.pages.dev/#1368297424086499359/1476675213067423980); [fit measures](https://marin-discord.pages.dev/#1368297424086499359/1476676306619072564).

Public teacher comparisons needed similar caution. A participant's GLM-4.6-versus-Qwen3-Coder-480B table combined different reports and included a projected harness score; it was not a matched ablation. Thinking format and architecture might matter more than a shared model-family name. An OpenThoughts-Agent contributor separately reported Kimi K2T and GLM 4.6/4.7 as strongest in their tests *after* generation setup was corrected. GLM thinking blocks could be malformed in 1–3% of outputs, and their vLLM setup required the DeepSeek reasoning parser. A teacher comparison can otherwise measure parser and template failures. [Cross-source caveat](https://marin-discord.pages.dev/#1476636771675541525/1476667771973669146); [format hypothesis](https://marin-discord.pages.dev/#1476636771675541525/1476669328782000333); [teacher observation](https://marin-discord.pages.dev/#1368297424086499359/1478175470431240222); [parser failures](https://marin-discord.pages.dev/#1368297424086499359/1478196842285236234).

## Cheap, verifiable data for basic capabilities

After observing 32B errors on elementary arithmetic inside agent rollouts, contributors proposed programmatically generating correct step-by-step arithmetic, unit conversion, regex, and bash examples for pretraining. A prospective 1T-token scale was an ambition, not a measured useful dose; an early estimate for a smaller bespoke set fell from under 50B to perhaps 5B tokens. The intended ablation was how many examples a generator can supply before the model memorizes its template instead of transferring the operation to natural tasks. Idle CPUs on training machines made deterministic generation attractive, while generating a trillion tokens with GPT-OSS was estimated at roughly $500,000 in compute. Large anonymous math datasets were treated cautiously when source code and trained-model evidence were absent. [Arithmetic motive](https://marin-discord.pages.dev/#1368297424086499359/1486977555842994246); [CPU objective](https://marin-discord.pages.dev/#1368297424086499359/1486979853608812714); [cost estimate](https://marin-discord.pages.dev/#1368297424086499359/1486983651047768145); [transfer ablation](https://marin-discord.pages.dev/#1368297424086499359/1486984614206640198); [dataset concern](https://marin-discord.pages.dev/#1368297424086499359/1487217376335233042).

Code World Model Python stack traces reached 583,733 rows and an estimated 42–54B tokens after 23.1% of shards; the stated 183–235B-token full-dataset size was a linear projection, not a completed count. SWE-ZERO produced 1,000 trajectories over ten SWE-rebench repositories. Its diversity check found 87.4% unique bash commands at the stated Jaccard threshold, and its mini-coder teacher reportedly exceeded 50% SWE-Bench pass@100. These measurements established candidate generation pipelines; neither demonstrated that the eventual pre/midtraining mix improved a student. [Stack-trace projection](https://marin-discord.pages.dev/#1368297424086499359/1501634667592421436); [SWE-ZERO MVP](https://marin-discord.pages.dev/#1368297424086499359/1492293100058706011).

## Data quantity, epoching, and mixture learning

In a long May exchange, contributors disputed whether a large advertised token count translates to new information. Dolma and Nemotron web corpora shared much of the same Common Crawl source material, and Nemotron's reported 25T training tokens included repeated epochs. An argument from data-constrained scaling work favored several repeats of good data over weak new data; a counterpoint was that benchmark overfitting can appear before IID loss degrades and that changing the domain mix becomes harder when useful buckets are already heavily repeated. No universal safe epoch count was established. [Corpus overlap](https://marin-discord.pages.dev/#1505202592966512843/1505302038353809529); [epoching objection](https://marin-discord.pages.dev/#1505202592966512843/1505962452591054848).

The proposed pipeline was to ingest candidate data, deduplicate and decontaminate it, label quality and domain, form quality-by-domain buckets, then learn the mixture. Mixture learning was described as learning how long to repeat high-value buckets before adding lower-value material, with quality depending on domain and target metrics. A small human “intruder” check favored new Luxical tags over Dolma tags, but used only 20 comparisons per variant: domain agreement was 10/20 versus 7/20, and quality agreement 8/20 versus 2/20. The author called it underpowered. A later plot linked higher code-quality quartiles with better coding-perplexity correlations; the plot itself was linked rather than reproduced in the archive. [Pipeline](https://marin-discord.pages.dev/#1505202592966512843/1505969827683110925); [mixture interpretation](https://marin-discord.pages.dev/#1505202592966512843/1505970767547072552); [small tagger audit](https://marin-discord.pages.dev/#1368297424086499359/1506396720748040273); [code-quality correlation](https://marin-discord.pages.dev/#1368297424086499359/1512624284869202051).

Participants separated compute-optimal model sizing from repeated-data exposure. Marin's MoE decision was said to use its own isoFLOP fits, with one 1e23-FLOP model near ten tokens per total parameter and 80 per active parameter. They debated whether Chinchilla's roughly 20 tokens per parameter could transfer to MoEs or extrapolate to larger dense models; different fitting approaches and possible specification errors yielded different forecasts. The thread ended without a universal ratio and emphasized fits for the actual architecture and data. [Marin MoE ratios](https://marin-discord.pages.dev/#1505202592966512843/1507452347461144706); [fit-method disagreement](https://marin-discord.pages.dev/#1505202592966512843/1507501046736355498); [unresolved specification question](https://marin-discord.pages.dev/#1505202592966512843/1507727130207715518).

Web graph features were proposed for future data selection. Common Crawl already used graph rank to allocate crawl budgets, and a paper on hub versus fringe pages prompted interest in boosting fringe sites within useful topical or language clusters. Reconstructing graph features for Marin's existing document pool was identified as unfinished work, not a tested improvement. [Crawl-budget method](https://marin-discord.pages.dev/#1368297424086499359/1520930909644259428); [implementation issue](https://marin-discord.pages.dev/#1368297424086499359/1521207946707730552).

## TaskTrove: source count is not verifier quality

TaskTrove collected Harbor-format agent tasks. In July, 43 candidate open datasets lacked usable verifiers; some had ground-truth tests to package, while others might require an LLM judge. By early September, version 4.8 reported 94 sources and about 1.7M tasks, with only 23 of 151 proposed competency categories covered. A proposed RL selection heuristic combined a large pass@16-to-pass@1 gap for a target student with a high stronger-model ceiling. These were inventory and working-hypothesis figures, not evidence that every task supplied a clean reward. [Verifier backlog](https://marin-discord.pages.dev/#1368297424086499359/1529499435321790555); [version 4.8](https://marin-discord.pages.dev/#1368297424086499359/1544475503052722179); [coverage map](https://marin-discord.pages.dev/#1368297424086499359/1545147565496999979); [reward-gap hypothesis](https://marin-discord.pages.dev/#1368297424086499359/1544012302431420416).

A task-level audit overturned the reassuring source-level curves. Of 10,000 QASPER tasks, 49.51% lacked the paper the agent was supposed to read, and 74.07% were `_copyN` duplicates of agent-visible instructions and questions. Its GPT-4o-mini judge had neither gold answer nor evidence spans, so its verdict required independently solving the question. An instruction-following citation source accepted prescribed citation markers even when their meaning was opaque and an agent could emit many markers to pass. Another 40-task audit across 20 sources labeled 14 broken or hackable, though its author thought the 16 “no model value” judgments were too strict. R2EGym had 293 tasks without problem text and 25 whose gold patch failed its own tests. [QASPER audit](https://marin-discord.pages.dev/#1368297424086499359/1545689065347620955); [citation exploit](https://marin-discord.pages.dev/#1368297424086499359/1545692801340022854); [40-task audit](https://marin-discord.pages.dev/#1368297424086499359/1545694628756586587); [R2EGym faults](https://marin-discord.pages.dev/#1545694628756586587/1545865917823582369).

The TaskTrove v4.13 response tested tasks or exact shared verifier signatures, removed 5,426 confirmed-invalid tasks, deprecated the full QASPER and STaQC populations, and made several verifiers return zero reward for missing output while still surfacing infrastructure failures as errors. The reported checks do not prove the remaining corpus defect-free. A contributor separately repaired CrossCodeEval by restoring cross-file context and changing a permissive prefix-based reward into a full-reference match, then was told to drop the 14 tasks whose context could not be restored. Reward semantics, task artifacts, and exact failure handling had to be checked together. [v4.13 changes](https://marin-discord.pages.dev/#1368297424086499359/1546234466203336856); [CrossCodeEval repair](https://marin-discord.pages.dev/#1546234466203336856/1547228679547920415); [drop unrecoverable tasks](https://marin-discord.pages.dev/#1546234466203336856/1547257723366670407).

The proposed QASPER rebuild returned to original papers, answer annotations, and evidence spans. Annotators sometimes disagreed even on whether a question was answerable; one cited original-paper audit found at least one correct annotation for 98% of sampled multi-answer questions, but only 75.8% of individual annotations correct. Participants proposed separate deterministic and judge-graded splits, explicit answer formats, evidence retrieval, and setup files that give the agent access to the paper without leaking gold answers or filling the prompt with the entire document. These were design proposals, not completed verifier results. [Annotation audit and reward options](https://marin-discord.pages.dev/#1545689065347620955/1548482359182237746); [verifier design](https://marin-discord.pages.dev/#1545689065347620955/1547046085799976960).

Other proposed task sources received narrower guidance. Text-to-SQL with a fixed database and result-set equivalence looked better suited to a non-agentic MarinSkyRL verifier than to TaskTrove; a contributor opened a PR and reported a small learnability check. Kaggle/OpenML-style tasks could use held-out labels, subject to data-rehosting rights and reproducible task templates. Contributors were asked to avoid direct LLM-mediated task generation with no reproducible script. [SQL placement](https://marin-discord.pages.dev/#1547004047100223608/1547023144353796148); [SQL PR](https://marin-discord.pages.dev/#1547004047100223608/1547651994716737597); [OpenML guidance](https://marin-discord.pages.dev/#1547218837404131359/1547258378093596734).

## Agent traces, provenance, and contamination

The agent-data work moved from one-off links toward registries of Harbor tasks and Terminus-2 trajectories. For a coding-expert cold start, one team reported that its Snowball checkpoint solved about five of 87 Terminal-Bench 2 tasks and aimed to raise that with SFT before RL. They considered GLM 5.3 rollouts on 37,000 Recursive Task Synthesis tasks; a 200-task pilot was checked, and the full rollout upload was later reported complete. That is a data-generation handoff, not a reported student improvement. Existing GLM 5.2 Terminus-2 traces were also offered, though their `analysis` and `plan` fields did not directly match the desired thinking-span format. [Cold-start problem](https://marin-discord.pages.dev/#1550321176381886535/1550609642114130021); [trace format](https://marin-discord.pages.dev/#1550321176381886535/1550630782517780513); [pilot](https://marin-discord.pages.dev/#1550321176381886535/1550701695510511647); [upload](https://marin-discord.pages.dev/#1550321176381886535/1551246758682828861).

Contributor-provided traces from open models were considered usable when uploaded in a standard messages format. Traces from closed models whose terms restrict distillation were excluded. For an existing 100k OpenThoughts-Agent SFT set, a reply found no direct use in Snowball's indexed pre/midtraining sources or the cited cold-start SFT list, while leaving open indirect duplication with AgentTrove or other sources. Dataset provenance remained a gap: participants noted that many TaskTrove subsets lacked a concise statement of origin and purpose. [Contribution format and terms](https://marin-discord.pages.dev/#1549486188870504459/1549541327019049032); [Snowball source check](https://marin-discord.pages.dev/#1550320126870556783/1550328443793571903); [provenance gap](https://marin-discord.pages.dev/#1550450414992891984/1550450425340108841).

An initial contamination report across Marin SFT sources flagged KernelGym rollouts against Terminal-Bench because both included ordinary PyTorch imports. The follow-up identified this as a false positive from boilerplate, demonstrating that an n-gram match is only a lead: contamination needs the matched span, task statement, and solution context. The thread did not resolve all other flagged datasets. [Initial report](https://marin-discord.pages.dev/#1368297424086499359/1549916057580474409); [boilerplate false positive](https://marin-discord.pages.dev/#1368297424086499359/1549917870551466135).
