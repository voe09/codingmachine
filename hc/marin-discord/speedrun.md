# #speedrun

Archive coverage: 2025-04-28–2026-05-15 (UTC); 656 messages, including 54 thread replies. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1364826908994568282).

## Purpose and fair comparisons

Speedrun began as a fixed-data, vary-the-training-recipe benchmark. A separate data-efficiency track was discussed but deferred so the first leaderboard could compare architectures and optimizers on the same distribution. It was intended as a low-cost gate and contributor entry point, not proof that a small-model result would survive at frontier scale. The framework could accept a different training implementation, including GPU code, if the submission produced comparable outputs. Early examples covered dense models at several sizes, an MoE, an optimizer variant, and GPU starter runs. [Fixed-data decision](https://marin-discord.pages.dev/#1364826908994568282/1369213661482057739); [framework flexibility](https://marin-discord.pages.dev/#1364826908994568282/1376622952832831538); [baseline set](https://marin-discord.pages.dev/#1364826908994568282/1373856247102832651).

The leaderboard's original two-axis result was loss against compute. Participants wanted a single “time or FLOPs to target loss” number for ranking, but worried that one target could hide the Pareto frontier or favor a particular model scale. One proposal was to report the FLOPs spent, final loss, and implied savings against a fixed baseline for a target loss, possibly at several target losses. A fitted baseline scaling law could turn the last measure into estimated baseline FLOPs divided by submitted FLOPs. The proposals required more than one point near the target to detect saturation and a trustworthy fit before a projected speedup could be interpreted literally. [Three-number proposal](https://marin-discord.pages.dev/#1364826908994568282/1370912768101716051); [several targets](https://marin-discord.pages.dev/#1364826908994568282/1371171869570502686); [baseline ratio](https://marin-discord.pages.dev/#1364826908994568282/1370637163867279451); [saturation concern](https://marin-discord.pages.dev/#1364826908994568282/1370648123281641593).

The choice of budget changes the leaderboard. One dashboard measure used hardware FLOP/s multiplied by time spent in training steps, which includes optimizer work and reflects actual utilization; that is not identical to theoretical model FLOPs. Participants worried that machine setup and environmental variance could create outliers. The proposed compromise was to accept proof-of-concept submissions on available hardware, then retest promising methods on controlled project hardware and at multiple sizes. Later discussion favored model FLOPs for some comparisons precisely because hardware-time results can vary with the environment. [Budget definition](https://marin-discord.pages.dev/#1364826908994568282/1414997323620159628) · [Open-hardware tradeoff](https://marin-discord.pages.dev/#1364826908994568282/1389487913561231401) · [Model-FLOP preference](https://marin-discord.pages.dev/#1364826908994568282/1438642091201663216).

The hardware measure was refined to sum *training step* times rather than count setup and preempted downtime, then multiply by the devices' peak FLOP/s. It intentionally penalizes a slow optimizer implementation even if that optimizer reaches lower loss in the same number of tokens. Muon illustrated the difference: early speedruns saw better token efficiency but slower training, and contributors identified unoptimized MFU and missing per-module learning-rate scaling as possible reasons not to read the chart as an optimizer-only verdict. Conversely, model-FLOP plots omit implementation overhead but can make scaling-law fits less sensitive to the particular cluster. The group wanted both views; neither was a universal “true” cost. [Step-time accounting](https://marin-discord.pages.dev/#1364826908994568282/1372677092029759620); [Muon trade-off](https://marin-discord.pages.dev/#1364826908994568282/1392227252523241523); [implementation caveat](https://marin-discord.pages.dev/#1364826908994568282/1413541429854076929); [per-module scaling gap](https://marin-discord.pages.dev/#1364826908994568282/1396889464441405490); [two-axis decision](https://marin-discord.pages.dev/#1364826908994568282/1427768097359659160).

Early GPU trials gave newcomers a sense of cost: 50M- and 75M-parameter models each ran 1,000 steps in roughly 900 and 1,330 seconds on the stated A100 setups, with memory limiting batch size before an abstract FLOP budget did. A 10–20M-parameter run could still be a useful implementation check, but the channel did not treat that alone as evidence for a production recipe. [GPU trial](https://marin-discord.pages.dev/#1364826908994568282/1372119403734237254) · [Contributor question](https://marin-discord.pages.dev/#1364826908994568282/1466159874546077787).

For outside contributors, preprocessing could dominate the experience before training began. A 16-core/64 GB machine stalled for more than two hours tokenizing roughly 97 MB of Paloma validation data, with many Ray tasks pending; a 32-core/128 GB machine finished quickly. Inspection showed each per-file task reserving 12 CPU cores on the 16-core machine. Changing that reservation to one core made the run finish in under ten minutes, and a moderated heuristic was proposed. The lesson was to separate benchmarked train-step compute from setup cost while still making setup feasible on modest machines. The channel also weighed attention-backend defaults on a single A100: cuDNN ran a 130M example in about 7h10m versus 7h50m for JAX_FLASH, but the starter stayed on JAX_FLASH to avoid a fragile NVTE install and preserve existing baseline comparability. [Paloma bottleneck](https://marin-discord.pages.dev/#1364826908994568282/1416574369739706529); [reservation test](https://marin-discord.pages.dev/#1364826908994568282/1416578574865137664); [backend timing and choice](https://marin-discord.pages.dev/#1364826908994568282/1444216530744377406); [starter rationale](https://marin-discord.pages.dev/#1364826908994568282/1444217760413388832).

One CReLU/CGeLU idea made this trade-off concrete. The proposer saw lower memory in a small proof of concept by reconstructing paired activations from one saved input. Reviewers noted that concatenated ReLU writes twice the activation data and can be bandwidth-bound, while checkpointing the entire MLP already recovers much of the claimed memory. The proposer acknowledged their experiment checkpointed inside the MLP instead. No end-to-end speedrun winner was reported, so the local memory observation should not be promoted to a training-efficiency gain. [Proposal and probe](https://marin-discord.pages.dev/#1364826908994568282/1374581830166118400); [bandwidth cost](https://marin-discord.pages.dev/#1364826908994568282/1374618072211787807); [checkpointing correction](https://marin-discord.pages.dev/#1364826908994568282/1374800570984038462).

## What to carry forward

The more reliable evidence came from *scaling-style speedruns*: compare methods across token-to-parameter ratios and compute budgets, rather than promoting a single lucky point. In one discussion, the best methods tended to improve loss at every tested token/parameter ratio. Scaling-law fits themselves need robust optimization and uncertainty checks; the group debated using a full loss-surface fit instead of only fitting curves inside the website. [Scaling-style recommendation](https://marin-discord.pages.dev/#1364826908994568282/1414997323620159628) · [Across-ratio observation](https://marin-discord.pages.dev/#1480569693805744219/1481311678917513236) · [Fit discussion](https://marin-discord.pages.dev/#1364826908994568282/1480569693805744219).

The scaling track was a pragmatic ladder: roughly one Chinchilla-style run per compute scale, often only five points, rather than an isoFLOPs sweep at each scale. That lowered the cost for contributors, but a method could change its own compute-optimal token/parameter ratio. A single lucky point or an uneven hyperparameter sweep could distort the forecast. The team proposed holding out at least one larger run, adding intermediate scales, and including deliberately worse architectures to test whether the instrument detected known regressions. NoPE variants blew up under RoPE-tuned optimizer settings; ReLU looked acceptable at small sizes but failed at the 1.2B point, exactly the sort of scale-dependent behavior a small-only test would miss. These negative controls do not prove every future ranking, but they helped test sensitivity. [Five-point ladder](https://marin-discord.pages.dev/#1480569693805744219/1481305258834792592); [compute-optimal caveat](https://marin-discord.pages.dev/#1480569693805744219/1481311076434972712); [negative-control plan](https://marin-discord.pages.dev/#1364826908994568282/1394531008367558747); [NoPE/ReLU results](https://marin-discord.pages.dev/#1364826908994568282/1394737274058703010).

The optimizer plots were hard to interpret in raw bits per byte: a meaningful compute saving can make a visually small loss change near a plateau. Participants added a relative-to-Adam view so scale-dependent advantages were more visible while keeping raw BPB available. They also distinguished three possibilities when curves sat close together: the metric was noisy, the plot hid an effect, or the methods genuinely differed little. An optimizer that speeds early fitting, one that stabilizes large runs, and one that reduces variance across data orders would have different scaling signatures; one fixed-seed curve cannot measure all three. Muon and Adam comparisons were especially sensitive to warmup and per-module learning-rate choices. [Measurement-versus-plot discussion](https://marin-discord.pages.dev/#1364826908994568282/1395067623024103424); [relative view](https://marin-discord.pages.dev/#1364826908994568282/1395183858504171733); [optimizer effect types](https://marin-discord.pages.dev/#1364826908994568282/1395117540094640328); [warmup caveat](https://marin-discord.pages.dev/#1364826908994568282/1413542886686855209).

Fit quality itself became an experimental target. A December dashboard bug put the Adam baseline off its own zero-relative line; it was fixed before interpreting the relative plot. The curves then showed bow-shaped residuals, prompting debate over a pure power law versus adding an asymptote. An asymptote might fit visible points better, but with few scales it was sensitive to initialization and could change the extrapolation substantially. Adding intermediate MuonH points moved one two-order-of-magnitude-away forecast from 0.766 to 0.764 BPB and raised the reported fit R² from 0.993 to 0.995. That is a fit-robustness check, not validation of the distant forecast; the proposed larger held-out run and retrospective leave-one-scale-out tests address extrapolation more directly. A later five-parameter loss-surface fitting proposal was explicitly unvalidated on this small speedrun sample. [Baseline bug](https://marin-discord.pages.dev/#1364826908994568282/1448803642760106035); [asymptote sensitivity](https://marin-discord.pages.dev/#1364826908994568282/1452131438756630569); [extra-point result](https://marin-discord.pages.dev/#1364826908994568282/1452033641675882676); [R² result](https://marin-discord.pages.dev/#1364826908994568282/1452034140844200027); [holdout proposal](https://marin-discord.pages.dev/#1364826908994568282/1450592228148773016); [five-parameter caveat](https://marin-discord.pages.dev/#1480569693805744219/1480571109463166976).

The attention-sinks submission illustrated a more mundane fit hazard. A 1.2B point had unusual runtime after a restart, and contributors investigated whether the chart summed downsampled W&B step times or whether a different attention kernel ran at that scale. They found the collection code used `scan_history`, which was intended to return the full series, but a few result JSONs still failed a timing sanity check and an issue was filed. The kernel/runtime question was not fully closed in the cited discussion. A scaling line can therefore be distorted by measurement plumbing or implementation choices even when its loss values are genuine. [Outlier report](https://marin-discord.pages.dev/#1364826908994568282/1425652309005832362); [history method](https://marin-discord.pages.dev/#1364826908994568282/1426465832128614450); [remaining discrepancy](https://marin-discord.pages.dev/#1364826908994568282/1426728581182263406).

The project also had to decide where experimental code lives. Keeping every speedrun implementation on the main branch creates ongoing maintenance work when Levanter changes. The proposed split was to maintain a readable default and a best recipe, while preserving historical experiments with linked result JSON, code, and W&B runs even if they live in branches or issues. Reproducible artifacts matter more than making every exploratory variant a permanent library API. [Code-retention proposal](https://marin-discord.pages.dev/#1364826908994568282/1473934758105972746) · [Artifact requirement](https://marin-discord.pages.dev/#1364826908994568282/1473938209942536355).
