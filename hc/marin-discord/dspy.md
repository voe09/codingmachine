Archive coverage: 2025-11-07–2026-07-06 (UTC); 116 messages, including 21 thread replies. Every exported message body and reply in this channel was reviewed. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1436412621040648222).

## Format following is not the same as format invariance

The collaboration asked whether Marin models could work better inside **DSPy programs**, which compose LLM calls with structured inputs, structured outputs, and downstream task checks. The research target became more precise over time: fine-tuning a small model to produce one known format is likely straightforward; the harder test is whether a model keeps solving the underlying task when asked to use a different or previously unseen format. That means measuring both parse/format validity **and task correctness**, rather than celebrating syntactically valid JSON that contains the wrong answer. It also means testing structured *inputs*, not only output schemas. [Initial goal](https://marin-discord.pages.dev/#1436412621040648222/1436413837833404518) · [Two distinct questions](https://marin-discord.pages.dev/#1436412621040648222/1440875961582092381) · [Input and output scope](https://marin-discord.pages.dev/#1436412621040648222/1439242355835142225) · [January restatement](https://marin-discord.pages.dev/#1436412621040648222/1463298066839900304).

TOON was discussed because it may use fewer tokens than JSON, not because the team had established it was better for small models. Contributors suspected that CSV- or TOON-like encodings can place related fields far apart in long structures, whereas JSON's local nesting may be more robust. They proposed comparing Chat/JSON, BAML, TOON, and perhaps grammar-constrained adapters on both real tasks and format accuracy; one participant said there were no concrete lower-scale TOON numbers yet. The generalization experiment would train on a diverse set of adapter formats and evaluate on unrelated tasks and out-of-domain adapters. Whether diverse-format SFT alone is sufficient, or a preference/reward-based method helps more, remained open. [Locality concern](https://marin-discord.pages.dev/#1436412621040648222/1437867376405250161) · [Format comparison proposal](https://marin-discord.pages.dev/#1436412621040648222/1439173934049394759) · [TOON uncertainty](https://marin-discord.pages.dev/#1436412621040648222/1440209180278653053) · [Out-of-domain test](https://marin-discord.pages.dev/#1436412621040648222/1439242610165284986).

The first SFT design discussed collecting traces from several tasks—roughly 1,000 examples each rather than all 3,000 from HotpotQA alone—so any gain would be less tied to one dataset. Suggested tasks included retrieval QA and structured extraction; deeply nested schemas were to be limited enough that context length did not dominate the comparison. The team wanted to measure each model's baseline format-error rate across adapters *before* choosing which model to train. By January 2026, wider-task SFT replication was described as a sanity run; preference data and format-specific DPO loss corrections were future ideas, not reported positive results. [Multi-task data design](https://marin-discord.pages.dev/#1436412621040648222/1439242610165284986) · [Nesting constraint](https://marin-discord.pages.dev/#1436412621040648222/1439440821417021591) · [January status](https://marin-discord.pages.dev/#1436412621040648222/1463298066839900304).

## Make program evaluation reproducible without forcing one abstraction

LangProBe was the favored realistic DSPy benchmark. The team separated base-model likelihood/perplexity evaluations, full-model evaluations through an OpenAI-compatible inference endpoint, and interactive RL environments; it did not want to force every evaluator into an RL-environment abstraction if that made detailed reports awkward. A `DSPyEvaluator` was proposed to consume a model endpoint and task/adapter configuration. This split matters because a model can improve in a program's full task while still failing a narrow formatting probe, or vice versa. The channel records an evaluator skeleton, a later PR, and working inference-server utilities, not a final benchmark table. [LangProBe direction](https://marin-discord.pages.dev/#1436412621040648222/1439286738714628156) · [Three evaluation surfaces](https://marin-discord.pages.dev/#1436412621040648222/1439738950037143734) · [Evaluator proposal](https://marin-discord.pages.dev/#1436412621040648222/1439743657757380629) · [Later tooling status](https://marin-discord.pages.dev/#1436412621040648222/1445299284999405580).

Building that evaluation/training loop exposed practical dependencies: a retriever-backed task needed a ColBERT service, the TPU inference endpoint initially produced empty DSPy histories, and trace extraction had to preserve the adapter-formatted messages. Participants discussed validating a whole DSPy program by its task metric, then deciding whether each predictor call should become a separate SFT example. They used GPU inference for iteration speed while improving TPU compatibility. Empty traces were a pipeline symptom, not evidence of model failure. [Pipeline problem](https://marin-discord.pages.dev/#1436412621040648222/1440996261565300839) · [Empty-history diagnosis](https://marin-discord.pages.dev/#1436412621040648222/1441189533457846382) · [Trace semantics](https://marin-discord.pages.dev/#1436412621040648222/1441193205843492904) · [GPU-first status](https://marin-discord.pages.dev/#1436412621040648222/1445299284999405580).

There was also an artifact-policy question: if the evaluator was to be a standard Marin post-training measure, merging it into main would require ongoing code quality and maintenance. If the outcome were only a paper or one-off experiment, a tagged branch and linked issue would be less burdensome. The DSPy collaborators wanted both a near-term experimental harness and training data, with high-quality evaluation support eventually in the main codebase. A proposed success criterion was that future Marin models outperform parameter-class peers on structured input/output tasks—not simply that an evaluator PR merges. [Maintenance distinction](https://marin-discord.pages.dev/#1436412621040648222/1463950948664610867) · [Collaboration goals](https://marin-discord.pages.dev/#1436412621040648222/1464059818095673487).

## Prompt optimization can alter the RL starting point

A later small-scale observation connected DSPy to RL: a standard prompt gave the largest Delphi model so little initial reward that an RL run showed essentially no signal. After DSPy's GEPA prompt optimizer found a better prompt, a subsequent RL run appeared to learn. This suggests that prompt/program optimization can move an environment from an uninformative starting reward distribution into a trainable one. The channel does not provide a controlled sweep, so it does not establish that GEPA is generally necessary or sufficient for RL. [GEPA-to-RL report](https://marin-discord.pages.dev/#1436412621040648222/1520172887133257779).
