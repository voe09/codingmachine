## Training-library boundaries

Levanter supplied JAX/TPU training while Marin supplied experiment orchestration and multislice workflows. Moving an experiment into Marin reportedly made multislice setup easier; this illustrates why research experiments need not all become library features. [Multislice experience](https://marin-discord.pages.dev/#1366985639743979541/1406768389342363668). The group debated modular transformer components versus a model researchers can readily copy and alter. Modular pieces help shared code review, but a *hackable* transformer was preferred for unanticipated architectures, with reusable pieces retained where they clearly helped. [Debate](https://marin-discord.pages.dev/#1366985639743979541/1410055248378069063) · [Direction](https://marin-discord.pages.dev/#1366985639743979541/1417667336441430097).

The monorepo migration showed how packaging details affect experiments. Levanter's `tpu` and `torch_test` extras were workspace-member extras, requiring `uv sync --package levanter`; a command carried over from the old submodule layout could select a broken Torch/CUDA combination. An ostensibly current installation also ran stale code until the local submodule was cloned. A Stanford lm-eval-harness fork lacked a function Levanter imported, while syncing it was held up by Torch/Accelerate dependencies. Source checkout, installed package, version pins, and CI coverage all need to agree. [Workspace extras](https://marin-discord.pages.dev/#1366985639743979541/1437534217604173935) · [Stale source](https://marin-discord.pages.dev/#1366985639743979541/1422791909281108088) · [Eval-harness fork](https://marin-discord.pages.dev/#1366985639743979541/1424777786211700830).

## Sharding, meshes, and evaluation

`best_effort_sharding` could factor a `(2, 2, 2)` array across six devices into a `(3, 1, 1, 2)` mesh, then silently drop the leading axis. Restoring that dimension was necessary for the intended layout. [Bug](https://marin-discord.pages.dev/#1366985639743979541/1405669806010536113) · [Fix direction](https://marin-discord.pages.dev/#1366985639743979541/1405673348498854170).

The move to `jax.set_mesh(mesh)` was not cosmetic: it requires arguments of *all* JIT calls to reside on devices in the active mesh, and JAX random operations JIT internally. A mixed-source dataset failed on incompatible CPU/TPU devices although single-source tests passed. Fixes reached `mixture.py` and another call site; a separate multi-host evaluation callback still appeared to hang, with rank-divergent work suspected rather than proved. Regression tests therefore need real mixtures and host topology. [Mesh semantics](https://marin-discord.pages.dev/#1424999289481859197/1425148014003093670) · [Test gap](https://marin-discord.pages.dev/#1424999289481859197/1425217571992371421) · [Callback hypothesis](https://marin-discord.pages.dev/#1424999289481859197/1425268343518269534).

The evaluation harness had a related boundary failure: a NumPy comparison encountered an array under the TPU default mesh. Moving that operation to a CPU context was a local remedy, but the design concern was an unclear handoff between host-side packing and device-side model evaluation. [Failure and remedy](https://marin-discord.pages.dev/#1366985639743979541/1427428860273885304) · [Boundary diagnosis](https://marin-discord.pages.dev/#1366985639743979541/1428050308348645611) · [Restructure proposal](https://marin-discord.pages.dev/#1366985639743979541/1428054784610402374). Haliax `axis_mapping` applies when a function is *traced*, not when its decorator is defined; wrapping only the definition in a temporary context does not affect a later call. [Tracing explanation](https://marin-discord.pages.dev/#1366985639743979541/1478477953800208670) · [Equivalent call-time patterns](https://marin-discord.pages.dev/#1366985639743979541/1478491199080890500). One developer later proposed explicit meshes and Equinox as possible replacements for some Haliax machinery; the archive records a preference, not a completed migration. [Migration idea](https://marin-discord.pages.dev/#1366985639743979541/1474121461974171719).

## Kernels, architecture, and performance

After a JAX 0.6.1 upgrade, one setup's model FLOP utilization reportedly fell from about 55% to 47%, but Ray also changed, so JAX was not isolated as the cause. The enduring practice is to pin and compare the full runtime after upgrades. [MFU discussion](https://marin-discord.pages.dev/#1366985639743979541/1382749347275604111). Attention-mask capabilities also constrained model research: SplashAttention's `ComputableMask` could express a static fixed-length prefix mask, but not obviously variable per-example prefixes or mixed SFT/UL2 patterns. An attention-sinks experiment changed length from 4096 to 4097, breaking a flash-attention block-size assumption; switching to another backend would confound its speed comparison. [Mask discussion](https://marin-discord.pages.dev/#1366985639743979541/1410851712612307055) · [Sink-token constraint](https://marin-discord.pages.dev/#1366985639743979541/1422023913982001174).

Gated DeltaNet obtained strong C4 English bits-per-byte in a 130M run, but at about three times the hardware FLOPs of comparable models. Training had crashed until tensor parallelism was enabled, and XLA warned of involuntary full rematerialization. Participants suspected inadequate FSDP, HBM pressure, and large FP32 intermediates in the untiled chunk rule, and recommended inspecting actual shardings. The channel does not establish which optimization ultimately worked. [Quality and cost](https://marin-discord.pages.dev/#1431126701055676558/1431126819465072690) · [Symptoms](https://marin-discord.pages.dev/#1431126701055676558/1431127278007484550) · [Inspection](https://marin-discord.pages.dev/#1431126701055676558/1431137628647850094).

Large-vocabulary logits consumed substantial memory for an RL workload, prompting chunked cross-entropy work. A fused softmax loss based on Pallas/Tokamax later became the Levanter and Grug default. Its author reported that it was *slower* than the reference in one benchmark, largely from rematerialization, but much more memory-efficient for large vocabularies; `reference` remained a fallback. This trades isolated speed for feasible end-to-end configurations, and a later Qwen3-8B/v5p-64 slowdown still required tuning. [Memory pressure](https://marin-discord.pages.dev/#1366985639743979541/1451458158756237396) · [Kernel report](https://marin-discord.pages.dev/#1366985639743979541/1467710224935817389) · [Regression](https://marin-discord.pages.dev/#1473406174933024810/1473465253240111369).

## Checkpoints and serving boundaries

A Llama-3.2-1B HF checkpoint appeared to lack an LM head, but its head was tied to token embeddings; setting `tie_word_embeddings=True` resolved that interpretation. [Tied embeddings](https://marin-discord.pages.dev/#1366985639743979541/1415483383189999748). An OLMo HF checkpoint loaded on one v5p-8 host but failed on v5p-64 with a fully-addressable-array error. The recommended change was to read safetensors as NumPy on the host before distributing, rather than use its JAX loader in that multi-host path. [Failure](https://marin-discord.pages.dev/#1366985639743979541/1424196855872356515) · [Diagnosis](https://marin-discord.pages.dev/#1366985639743979541/1424497102393704563).

After preemption, TensorStore tried to resume from a checkpoint whose chunk contained too little data, consistent with an interrupted write. Falling back to an earlier checkpoint was suggested; participants expected a completion sentinel or equivalent so incomplete checkpoints would not be selected. The final fix is not shown. [Symptom](https://marin-discord.pages.dev/#1366985639743979541/1429978862200291399) · [Recovery concern](https://marin-discord.pages.dev/#1366985639743979541/1429993444733878353). Direct HF loading worked for most non-Grug models, avoiding unnecessary conversion, but repeated CDN timeouts made loads slow. A cached GCS URL and HF authentication were suggested; an existing `download_model_step` was not automatic in this path. One later GCP-route test loaded an 8B model in roughly 30 seconds. [Timeout](https://marin-discord.pages.dev/#1366985639743979541/1464049345635684475) · [Download step](https://marin-discord.pages.dev/#1366985639743979541/1464304920328146964) · [Speed report](https://marin-discord.pages.dev/#1464439742912270491/1464440371550490668).

Levanter's inference scheduler did not support multi-host serving, despite multi-host *training* support. That limited in-loop generation evaluation for larger DPO jobs. Levanter inference was also considered much slower than vLLM, with cache updates identified as a weakness. Yet vLLM's TPU path lacked standalone `prompt_logprobs` needed to score completions without generation; `logprobs` returned alongside generation was a different API. Fork PRs were drafted but not yet machine-tested in the channel. Placement, throughput, and API completeness were distinct problems. [Scheduler limit](https://marin-discord.pages.dev/#1467690675897372927/1467692865454084250) · [Cache weakness](https://marin-discord.pages.dev/#1366985639743979541/1493699112783188180) · [Scoring gap](https://marin-discord.pages.dev/#1493702629774069952/1493704880081207386) · [PR status](https://marin-discord.pages.dev/#1366985639743979541/1494155866952171701).

## LoRA/DPO: a corrected numerical case study

In April 2026, LoRA DPO on v5p-8 learned much less effectively than seemingly comparable v6e-8 or larger v5p runs. The team checked dataset hashes, initial parameters, global batch, microbatching, fused CE blocks, gradient norms, and full fine-tuning. Identical initial losses and nearly equal gradient *norms* did not mean equal gradients: signed per-module sums differed at step zero. Full fine-tuning on v5p-8 learned, localizing the symptom to this LoRA path rather than generic DPO or hardware failure. [Step-zero comparison](https://marin-discord.pages.dev/#1493355484055474186/1493494570082893885) · [Full-FT control](https://marin-discord.pages.dev/#1493355484055474186/1493527314854576128).

Several plausible explanations failed. Upcasting a suspected CE accumulation, forcing one CE batch block, and using FP32 parameters/compute did not repair the original bad run. Generated configs had silently changed LoRA rank from 64 to 16, but restoring it did not solve the divergence either. Changing the v5p-8 mesh from `{data:4, model:1}` to `{data:1, model:4}`, then `{data:2, model:2}`, restored learning. This suggested a mesh-dependent numerical path, while the first offending backward operation remained unidentified. [Rank correction](https://marin-discord.pages.dev/#1493355484055474186/1493662025384071358) · [Ruled-out CE story](https://marin-discord.pages.dev/#1494819738004623500/1494819835690094684) · [Mesh result](https://marin-discord.pages.dev/#1494819738004623500/1494819926098055239) · [Caveat](https://marin-discord.pages.dev/#1494819738004623500/1494965743433814108).

Permuting logical device order changed XLA reduction/fusion choices and exposed an initialization-sensitive issue in modules sharded on `embed_dim` as the output dimension. The practical response reversed which LoRA factor starts at zero and which starts with Gaussian noise. Follow-up sweeps reported equal or better validation loss and comparable LM-as-judge results; the DPO default was changed accordingly. This is an empirical fix, not proof of an XLA bug or a universal preference for reversed initialization. The learning is to track step-zero tensors and test each compiler story against controlled alternatives before accepting it. [Device order](https://marin-discord.pages.dev/#1366985639743979541/1495202551761731644) · [Localization](https://marin-discord.pages.dev/#1366985639743979541/1495643793142190220) · [Sweep outcome](https://marin-discord.pages.dev/#1366985639743979541/1498901116404895774).

## Training length with mixtures

The `epoch` trainer option was removed because a single epoch count is ill-defined for mixed-source training; the caller instead specifies steps. Memorization studies and post-training still benefit from reasoning about repeated data exposure. The proposed shallow helper would calculate steps from tokenized data and a desired repetition count, rather than add a universal epoch knob. Tokenization began recording token counts in `.stats.json` to avoid rescanning the dataset. [Removal rationale](https://marin-discord.pages.dev/#1366985639743979541/1467066021926932480) · [Mixture caveat](https://marin-discord.pages.dev/#1366985639743979541/1467227848782774272) · [Helper proposal](https://marin-discord.pages.dev/#1366985639743979541/1467229744192815206) · [Token metadata](https://marin-discord.pages.dev/#1467229744192815206/1467230498114764810).
