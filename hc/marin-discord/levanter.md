## Training library boundaries and performance

Levanter supplied the JAX/TPU training layer while Marin provided experiment orchestration and multislice workflows. A contributor reported that moving an experiment from Levanter into Marin made multislice setup easier, which illustrates the intended division of responsibilities rather than a reason to merge every experiment into the library. This later became a monorepo/workspace design question shared with `#code-talk`. [User experience](https://marin-discord.pages.dev/#1366985639743979541/1406768389342363668).

Version and dependency changes had measurable performance or correctness consequences. One JAX 0.6.1 upgrade reportedly dropped model FLOP utilization from about 55% to 47% in the tested setup; an early MMLU error was traced to an old Haliax installation despite a matching project configuration. These incidents argued for measuring real training throughput after runtime upgrades and verifying the environment actually imports the intended package versions. [JAX regression](https://marin-discord.pages.dev/#1366985639743979541/1382601775038599239) · [Haliax diagnosis](https://marin-discord.pages.dev/#1366985639743979541/1367004150050852946).

A fused softmax-loss kernel based on Pallas/Tokamax work became the default in Levanter and Grug. The report said it was slower than the reference in one benchmark, largely because of rematerialization, but dramatically more memory-efficient for large vocabularies. That tradeoff can enable otherwise impossible batch, vocabulary, or model configurations; a faster isolated kernel is not always the better training-stack choice. [Kernel report](https://marin-discord.pages.dev/#1366985639743979541/1467710224935817389).

## Numerical and integration debugging

For a LoRA training divergence on v5p-8 and v6e-8, the investigation explicitly varied the dataset, gradient accumulation/microbatch, LoRA versus full fine-tuning, fused cross-entropy and its block size, and TPU topology. DPO curves matching on larger v5p-16 and v6e-16 configurations helped narrow the symptom but did not establish a simple universal cause. This is a useful debugging pattern: isolate topology, numerical kernel, and algorithmic changes before changing hyperparameters to hide a divergence. [Debugging matrix](https://marin-discord.pages.dev/#1366985639743979541/1494464722299519136).

Inference and model-loading work exposed several boundary issues. Levanter could read Hugging Face weights directly for most non-Grug models, avoiding unnecessary checkpoint conversion, though network timeouts could still interrupt loads. The group also asked how multi-host generation evaluation should interact with a training job when the inference engine had different placement and performance constraints. Both cases show why a training library needs explicit interfaces to external model artifacts and serving systems. [Direct weight loading](https://marin-discord.pages.dev/#1366985639743979541/1464321437086122137) · [Generation placement](https://marin-discord.pages.dev/#1366985639743979541/1467687110311022636).

The channel also contains low-level questions about Haliax axis-mapping context scope and dependency conflicts. Those discussions should be read as version- and call-site-specific debugging, not timeless API guarantees; the durable lesson is to test sharding behavior inside the compiled function and keep a minimal reproduction when a context manager or tracing boundary behaves unexpectedly. [Axis-mapping question](https://marin-discord.pages.dev/#1366985639743979541/1478477402110955734).
