# #flex-slice

Archive coverage: 2025-07-28–2025-08-16 (UTC); 11 messages. Every exported message body in this channel was reviewed. [Open channel in Discord](https://discord.com/channels/1354881461060243556/1379953659588382783).

The problem was training when preemptible TPU slices come and go. A proposed longer-term approach resembled **DiLoCo**: hand data chunks and a weight generation to separate slices, let them train locally, then periodically average their weights. The author noted that changing slice count or size would give up strict reproducibility and left the outer-step behavior uncertain. This was a design sketch, not the implementation that the channel later reported. [Decentralized proposal](https://marin-discord.pages.dev/#1379953659588382783/1399467802900955147).

The first delivered Levanter “flex multislice” mechanism was simpler: request a sequence such as one, two, four, or eight slices; the run restarts at intervals as it moves toward the available count, and after a crash it can fall back to the previous count before trying to scale up again. The discussion did not establish support for changing batch size at those transitions; the feature was described as most useful when memory was not the limiting constraint. This trades uninterrupted execution for adaptation to volatile capacity, while retaining the restart/checkpoint semantics of ordinary training.
